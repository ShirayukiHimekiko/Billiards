## 3. 方案 A：能力基接口 `IPropComponent`

### 3.1 问题

`GetComponents<MonoBehaviour>()` 会取回同一 GameObject 上**所有** MonoBehaviour（含非道具能力组件），语义过宽，收集范围不受控，再靠后续 `is` 判断筛选。

### 3.2 设计

新增基接口（`Core/Prop/Components/IPropComponent.cs`）：

```csharp
namespace GameLogic
{
    /// <summary>
    /// 道具 Prefab 上所有能力组件的共同基接口，用于统一收集与查询。
    /// </summary>
    public interface IPropComponent
    {
    }
}
```

两个既有能力接口改为继承它：

```csharp
public interface IPropSimulationProvider : IPropComponent { /* 现有成员不变 */ }
public interface IPropAvailabilityPresentation : IPropComponent { /* 现有成员不变 */ }
```

`PropObject` 改为：

```csharp
private IPropComponent[] _features;

/// <summary>
/// 应用道具的台面位置与显示尺寸，并缓存能力组件。
/// </summary>
public void Initialize(PropPlacementData data)
{
    // ... 校验 SpriteRenderer ...
    _features = GetComponents<IPropComponent>();
    _availabilityPresentation = GetFeature<IPropAvailabilityPresentation>();
    transform.localPosition = data.Position;
    transform.localScale = Vector3.one * (data.VisualDiameter / _renderer.sprite.bounds.size.x);
    SetAvailable(true);
}

/// <summary>
/// 从道具同物体的能力组件中取得唯一的指定功能。
/// </summary>
public T GetFeature<T>() where T : class, IPropComponent
{
    T result = null;

    foreach (IPropComponent feature in _features)
    {
        if (feature is T match)
        {
            if (result != null)
            {
                throw new InvalidOperationException($"道具 {name} 存在多个 {typeof(T).Name} 功能组件。");
            }

            result = match;
        }
    }

    return result;
}
```

### 3.3 为什么用空接口，而不是基类或直接筛选

- **空接口不是「机械加接口」**：它承担 Unity 类型化收集的实际职责——`GetComponents<IPropComponent>()` 把收集范围收敛为道具能力组件。若不引入它，只能退回 `GetComponents<MonoBehaviour>()` + 双接口 `is` 判断。
- **不用基类 `PropComponentBase : MonoBehaviour`**：当前 9 个能力组件没有任何共享状态或生命周期（与球的 `BallComponentBase` 需要 `Ball`/`Config`/`ResetFeature` 不同）。无共享成员时建基类属空壳继承，与项目「不机械增加抽象层」的约定冲突。后续若出现共享初始化需求再加不迟。
- **与球组件范式对齐**：`IPropComponent` + `XxxPropComponent` 对应 `BallComponentBase` + `XxxComponent`，命名与结构一致。

## 5. 方案 C：`Core/Prop/` 目录分类

目标结构：

```text
Core/Prop/
├── PropObject.cs                    道具实例统一入口
├── Components/                      Prefab 能力组件及其契约
│   ├── IPropComponent.cs            新增：所有能力组件的基接口
│   ├── IPropSimulationProvider.cs   提供无状态效果规格
│   ├── IPropAvailabilityPresentation.cs  可选可用状态表现
│   └── XxxPropComponent.cs × 9
└── Effects/                         无状态效果策略与规格
    ├── IPropEffect.cs               效果契约（含 IPropShotEffect）
    ├── PropEffectSpec.cs
    ├── PropEffectResult.cs
    └── XxxPropEffect.cs × 9
```

分类依据：

- `Components/`：挂在 Prefab 上的 MonoBehaviour 能力组件及其契约——「能力」即 Unity 组合单位。
- `Effects/`：无场景依赖、无实例可变状态的效果策略与规格/结果，供真实世界与预测副本共享。
- `PropObject.cs` 留在 `Core/Prop/` 根：它是道具实例的统一入口与表现，不是能力组件本身。

## 6. Module 归属核查

**结论：没有需要迁入 Module 的文件。** 当前 Module / Core 划分已符合《Module 与 Core 脚本摆放规范》v0.5。

| 文件 | 建议归属 | 依据 |
|---|---|---|
| `PropManager`、`PropEffectKind`、`PropKindConverter` | `Module/PropModule/`（现状） | Manager 与逻辑枚举、唯一转换器属模块管理内容 |
| `PropPlacementData` | `Module/LevelModule/`（现状） | 关卡聚合数据与配置快照 |
| `IPropEffect`、`PropEffectSpec`、`PropEffectResult`、`XxxPropEffect` | `Core/Prop/Effects/` | 道具行为契约与策略，服务真实模拟与预测；v0.5 规范明确「不为了接口名称把它单独搬到 Module」 |
| `IPropComponent`、`IPropSimulationProvider`、`IPropAvailabilityPresentation`、`XxxPropComponent` | `Core/Prop/Components/` | Prefab 能力组件及其契约，属 Core 对象行为 |
| `PropObject` | `Core/Prop/` | 道具实例统一入口 |

**可讨论项（本次不建议）**：若希望把「道具管理契约与快照」整体集中到 PropModule，可考虑迁 `PropEffectSpec` / `PropEffectResult`。但它们由 Core 能力组件创建、由 Core `PhysicsWorld` 消费，迁入 Module 会让 Core→Module 依赖方向倒置，故维持 Core。

## 8. 影响与风险

1. **Prefab 引用现状**：`Assets/AssetRaw/Actor/Prop/` 下 9 个 Prefab 目前仍指向**已删除**的 `GameLogic.FlipProp`（8 个）与 `GameLogic.KeyProp`（1 个），即 Missing Script；它们**尚未引用**本次要改名的 `XxxPropAbility`。因此本次改名不会破坏 Prefab，但也说明 Prefab 迁移仍在待办。
   - **建议顺序**：先完成本方案的改名与分类，再把 Prefab 一次性迁移到改名后的 `XxxPropComponent`，避免先按旧名绑、再改第二次。
2. **文件移动必须经 Unity Pipeline**：项目约定 Assets 内移动文件须保留 `.meta`/GUID。当前 `Library/Pipeline/` 下只有 `eval-usage.jsonl`，**无端口描述文件**（Unity Editor 未运行），移动需在 Editor + Pipeline 就绪后执行；禁止用文本方式挪动 `.cs.meta`。
3. **命名歧义**：`XxxPropComponent` 与 Unity `Component` 同名易混，但项目球组件已用此后缀，保持一致优于另起风格。
4. **无逻辑变更**：本方案只调整类型关系、命名与目录，不改变效果行为与 `PropUses` / `EffectRemaining` 等运行时语义，也不涉及此前发现的三处设计问题（Flip/Reverse 等价、Freeze/FastChange 共用倍率、Restore 只复位半径）。
