## 2. 实施方案

### 阶段 A：迁移 9 个道具 Prefab（必须通过 Unity Pipeline）

对每个 Prefab 执行：

1. 移除旧道具脚本组件（`GameLogic.FlipProp` / `GameLogic.KeyProp`）。
2. 添加 `PropObject` 组件，并把 `_renderer` 绑定到同物体的 `SpriteRenderer`。
3. 添加表中对应的 `XxxPropAbility` 组件。
4. 保存 Prefab，复查层级、组件与引用。

因 `PropBase : PropObject`，旧 Prefab 上已有的 `_renderer` 序列化字段在替换脚本类型后可按同名字段保留，但仍以 Pipeline 操作结果为准。

### 阶段 B：清理旧入口（纯代码 + 资源删除）

1. `PropManager.InitializeAsync`：删除 `view is PropBase` 与 `PropEffects.Get(data.Kind)` 回退分支，缺失 `IPropSimulationProvider` 时直接抛出带道具 ID 与 Prefab 地址的异常。
2. 删除 `PropBase.cs`、`FlipProp.cs`、`KeyProp.cs`、`PropEffects.cs`。
3. 删除已无引用的 `UnsupportedPropEffect.cs`。
4. 保留 `PropEffectKind`、`PropKindConverter`、`PropManager.Sync/GetKeyStates` 中基于 `Kind` 的判断：它们承担配置校验与 UI 状态标识的数据职责，原方案 2.3 节明确要求保留。

阶段 B 必须在阶段 A 全部完成之后执行，否则 Prefab 上旧脚本会变成 Missing Script。

## 3. 风险与边界

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| Prefab 迁移引入 Missing Script | 移除旧脚本后若未补 `PropObject`，Prefab 失效 | 同一 Prefab 内移除与添加成组完成，迁移后逐一复查 |
| 迁移与清理顺序错乱 | 先删旧类再迁移，Prefab 直接损坏 | 严格按 A -> B 顺序执行 |
| `_renderer` 引用丢失 | 替换脚本类型后字段未保留 | 通过 Pipeline 显式重新绑定并复查 |
| 误删仍被引用的类型 | `PropEffectKind` / `PropKindConverter` 仍服务配置与 UI | 仅删确认无引用的四个旧类型与 `UnsupportedPropEffect` |
