# 数学桌球：黑球入洞、六洞状态与几何解锁架构方案

日期：2026-10-06 · 任务等级：L4 · 状态：最新玩法已整理，实施建议待确认。

本轮只更新方案文档，未修改业务代码、配置、Prefab、材质或场景，未导表、编译、测试或运行 Unity。旧版检查记录只适用于旧版实现。

## 1. 用户已确认的玩法

1. **通关条件为本关所有黑球成功入洞。** 几何图形完成数量、解锁数量和道具使用数量都不能替代这个条件。
2. **玩家击打白球，白球通过碰撞推动黑球入洞。** 玩家不直接给黑球提交击球输入。
3. 桌面固定六个球洞，位置为常规桌球的四个角洞与两侧中洞；当前横向长桌使用上、下长边的中点作为中洞。
4. 球洞具有四种状态：上锁不能进、解锁可以进、已进黑球不能再进、不允许使用。
5. 用户的“解释道具／解释洞”已澄清为**触发道具／解锁球洞**。内切和外切对应几何交互条件，达成后产生效果，不再直接作为通关目标。
6. 沿用前轮要求：一关允许多个图形，每个图形各自只有一种几何条件；PropManager 管理道具，翻转道具继承 PropBase，并适当放大；库边反弹；预测采用随力度变化的虚线与末端圆点。

本方案取代[上一版多图形目标方案](数学桌球-Prop管理与互斥目标反弹预测方案.md)中“全部图形完成即通关”“几何达成立即停球”“下一杆恢复白球出生点”的流程。普通下一杆如何摆球按本方案第 6 节处理，几何规则按触发条件管理。

## 2. 建议随本方案一起确认的细节

下面是实施建议，尚不是用户逐项指定的规则：

| 事项 | 建议 |
|---|---|
| 不允许使用的洞 | Disabled，整局不能通过几何条件解锁 |
| 不能进球的洞 | Locked、Occupied、Disabled 均显示封闭口，并在口部反弹，不能默默吞球 |
| 几何条件作用球 | 初版由白球达成；规则数据可限制允许的球类型，暂不让黑球自动解锁 |
| 解锁和道具触发后的运动 | 更新对应状态／效果后继续模拟，不全桌停球 |
| 黑球入洞后的运动 | 移除这一颗黑球，其他球继续；全部黑球入洞时结束本局 |
| 解锁持续时间 | 解锁进度在本局后续击球中保留，重开恢复初始洞状态 |
| 普通下一杆 | 所有活动球停稳后，保留停球位置，从白球当前位置击球 |
| 白球落洞 | 按犯规处理，不增加黑球进度、不占用洞；本杆其余球停稳后将白球复位到合法出生点；最后黑球与白球同杆入洞的胜负优先级另行确认 |
| 翻转道具大小 | 先放大为原来的 1.3 倍，可见尺寸与触发半径同步扩大，数值可再调 |
| 黑球尺寸 | 初版固定半径；保留白球已有的大小变化及趋势翻转 |

仍未明确的规则不要硬编码成已确认结果，尤其是白球犯规、同杆最后黑球入洞和犯规的结算顺序。方案确认前不写实现。

## 3. 六个球洞的位置与身份

洞位置由台面尺寸与固定槽位确定，关卡只配置槽位状态和关联解锁规则。设计位置不随图形移动，不能把解锁图形放在哪里就在那里生成一个洞。

以横向长桌局部坐标为例，槽位排列如下：

```text
左上角洞 ───── 上中洞 ───── 右上角洞
│                                  │
│              桌面                │
│                                  │
左下角洞 ───── 下中洞 ───── 右下角洞
```

六个槽位使用稳定 PocketId，例如 TopLeft、TopMiddle、TopRight、BottomLeft、BottomMiddle、BottomRight。物理口部宽度、圆心偏移与吸收区域需根据 Prefab 的桌边和洞口形状设置，但始终归属这六个槽位。

桌面缩放后，显示与碰撞统一使用 LevelManager 提供的局部坐标布局。当前原型的完整矩形边界需要改为带六个口部的库边布局：有效球洞入口必须有真实通道，不能在同一位置仍保留完整反弹墙。

## 4. 球洞四状态及转换

使用单一枚举 `PocketState`，避免 Locked、CanEnter、Used、Disabled 等布尔值出现互相矛盾的组合。

| 状态 | 能收黑球 | 能被解锁 | 建议外观与碰撞 |
|---|---|---|---|
| Locked（上锁） | 否 | 是 | 锁标记与封口，洞口反弹 |
| Unlocked（解锁可用） | 是，一颗 | 已解锁，无需重复触发 | 开放洞口，进入吸收区后提交入洞 |
| Occupied（已进黑球） | 否 | 否 | 黑球完成标记与封口，后续球反弹 |
| Disabled（不允许使用） | 否 | 否 | 禁用标记与封口，整局不参与接球 |

正常转换为 `Locked → Unlocked → Occupied`。Unlocked 可作为初始状态；Disabled 不走解锁链。初版建议不配置初始 Occupied，以免与本关初始黑球数量发生歧义。重开恢复配置初始状态并清空入洞记录。

PocketManager 保存洞状态与占用黑球 BallId，Session 保存本局球和洞状态快照；二者共享同一个运行状态来源，UI 不维护自己的可进球开关。

**入洞必须原子提交：**核对该洞仍 Unlocked、该黑球仍在桌面，随后一起更新洞为 Occupied、记录 OccupantBallId、黑球生命周期为 Pocketed，并更新进度。不能先播放隐藏动画后再决定洞能否收球。

同一洞同一模拟步接近两颗黑球时，按最早到达时间提交第一颗；时间完全相同时以稳定 BallId 决定归属并重新查询另一颗的封口反弹。一个洞不能收两颗，一颗球不能重复计数。

## 5. 几何条件用于触发与解锁

几何规则数据从通关目标改为 `GeometryInteractionData`：包含 RuleId、图形几何、唯一 ConditionKind、容差、允许作用球类型、关联效果，以及被影响的 PropId 或 PocketId。

每个图形只允许一种条件；一关可以有多个图形，分别关联不同道具或不同球洞。几何图形位置与六个洞的位置独立，通过 ID 关联。当前默认一条规则对应一个作用对象；若后续需要一次解锁多个洞，再将关联扩为明确的效果列表。

流程为：`白球满足图形几何条件 → 返回交互事件 → 触发关联道具或解锁指定球洞 → 刷新表现和预测状态`。几何达成不会直接设置 Won，不移除黑球，也不直接增加入洞数量。

项目现有数学类型为三角形内切圆 Inscribed 和外接圆 Circumscribed。用户已确认它们承担触发／解锁职责，但“外切”是否指三角形外接圆或两个圆外切仍需在实施前统一术语；本轮沿用现有公式作为建议，不将两种不同数学条件混用。初版建议支持多个现有三角形，其他图形要先明确几何定义。

为了兼容前轮“不符合切法则反弹、符合则放行”的要求，图形对应的交互圆可保留条件阻挡。先判断当前接近能否达到该图形的有效条件，能达到则允许进入并在真实达成时触发；不能达到则在接触处反弹。触发一次后，该解锁图形建议显示已完成标记并取消阻挡；Disabled 洞不能因任何交互改为可用。

该局部前向查询暂时关闭正在评估的这一个交互圆的阻挡，仍处理球碰撞、库边、道具和洞状态。到该接近区间结束、接触其他尚未完成的交互圆、作用白球离桌或所有球静止时终止，禁止递归调用另一轮放行探测。预测只修改副本，不提前解锁真实洞。

PropBase 继续描述公共初始化、效果与复位；FlipProp 的效果是反转白球大小趋势。**接触触发与几何触发通过配置选择一种**，不能因为保留旧道具接触检测而在同一事件里翻转两次。解锁图形与道具类型可复用同一个规则求解器，球洞有自己的状态与捕获规则，不要求继承 PropBase。

每局一次的洞解锁与每杆一次的翻转道具使用是不同生命周期：解锁效果一旦完成就保持；翻转道具按原约定每杆复位，若采用几何触发，其本杆消费标记也一起复位。

## 6. 通关、杆次与进度

关卡初始化时记录全部目标黑球的稳定 BallId 集合。通关判定只检查这个集合中的每一颗是否已合法入洞；不能使用场景剩余 GameObject 数量或所有洞是否占满来替代。

```text
准备关卡、白球、黑球、六洞、道具与几何规则
→ 白球瞄准、蓄力、出杆，消耗一杆
→ 同步模拟所有活动球
→ 按时序处理几何触发、碰撞、反弹与入洞
→ 所有黑球合法入洞：记录通关并结束本局
→ 仍有黑球：等所有活动球停止，再允许下一杆
→ 杆数耗尽且本杆处理完毕仍有黑球：失败
```

建议不因某颗黑球入洞而全桌停球，允许同一杆依次把多颗黑球打进不同洞。没有入洞的一杆也会改变桌面布局，正常停球后不自动把黑球送回出生位置。

此前“每次几何成功停球、全部图形完成通关”不再使用。解锁或入洞进度在本局后续击球中保留；重新开始恢复球出生布局、洞初始状态、道具和所有交互规则。

MaxShots 继续由关卡配置决定。多球碰撞后可以一杆进多球，因此不再按“每个目标至少一杆”的旧逻辑规定杆数下限；要结合摆位、解锁成本与容错调参。

**数量约束：**一个洞整局最多收一颗黑球，所以初始目标黑球数量最多为六，且不能超过初始可用加本局可解锁的洞总数。禁用洞和永远无法解锁的洞不计入容量。该约束仅说明容量足够，不能证明摆位、尺寸与解锁依赖可解。

若球洞限制接收特定 BallId 或类型，还要判断可接收对象的分配是否存在；本轮未要求指定黑球必须进指定洞，默认任意黑球可进入任意当时 Unlocked 的洞。

## 7. 黑球碰撞、入洞与反弹

当前实现只有一个白球：BallManager 只持有 WhiteBall，BallBase 要求每颗球都绑定 Shoot 和白球模拟组件，并将外观直接绑定白球增长趋势。这些约定不能直接套到被动黑球。

建议职责调整如下：

| 对象 | 拟职责 |
|---|---|
| BallBase | 通用球 ID、球类型、位置、速度、半径、显示与生命周期；不强制所有球拥有输入能力 |
| WhiteBall : BallBase | 组合击球输入和大小变化能力，玩家唯一可击打的球 |
| BlackBall : BallBase | 固定大小的被动目标球，接受碰撞传来的速度，可被洞捕获，没有玩家输入 |
| BallManager | 管理白球与黑球集合，提供活动球数据与入洞进度，绑定／释放所有实例 |
| BilliardsSimulation | 用同一个世界状态同步推进所有球、洞与交互规则 |
| BilliardsContactQuery | 求球球、球库边、球交互圆、球洞入口的最早事件时刻 |

初版建议采用二维圆球的法线冲量传递，质量由配置提供，默认等质量；暂不新增旋转、侧旋或真实台球的完整摩擦模型。白球半径变化不自动改变质量，避免无意改变碰撞能量。

碰撞计算使用两颗球的相对位置、相对速度与半径之和，处理两个运动球或运动球撞静止球；黑球之间也会碰撞。不能仅反射白球并给黑球一个写死方向，也不能在黑球被碰后重复调用给白球使用的 Begin 力度接口。

真实模拟与预测使用一致的固定步和连续接触方法，推进所有活动球到当前全桌最早事件时刻，再更新受影响球与状态并重查剩余时间。初版几何交互限制白球，黑球仍要参与与白球、其他黑球和库边的碰撞。

Unlocked 洞在入口范围内开放捕获路径；捕获区、洞口通过宽度和球半径条件独立配置，必须让整个黑球能够进入洞口。只擦过洞边不等于入洞；太大的球不能被一个视觉上更小的洞直接吸收。

合法进球候选应优先于同一入口处的普通库边反射。Locked、Occupied、Disabled 洞则启用封口阻挡，始终不生成合法捕获事件。口部之外的库边照常反弹，洞口两侧的边角仍作为碰撞几何处理。

白球增长贴边、球体相互挤压和零时间接触要有确定的约束处理。建议增长受空间约束时暂停该方向的增长，离开接触后恢复趋势；不靠连续翻转速度来修复增长穿透。后续验证应覆盖多球链式接触，而不是只延用单白球的固定 8 次事件循环。

## 8. 同刻事件与状态提交

以事件发生时间排序，只有时刻相同时才使用固定规则：

1. 几何交互或道具效果达成，提交对应效果；如果影响洞状态或球半径趋势，重新查询同刻剩余候选。
2. 对当前 Unlocked 洞提交合法黑球捕获；同洞竞争按 BallId 确定归属，一次提交后洞立即 Occupied，其他球重新处理封口接触。
3. 处理白球入洞候选，记录犯规建议状态；不改洞的黑球占用状态。
4. 对仍在桌面的球解算球球、交互圆、封闭洞口及库边接触。
5. 汇总黑球进度与本杆状态，依据确认后的犯规优先级结算；正常下一杆等活动球全部停止。

不能让 Locked 洞先吞球再等待解锁动画；若解锁与进洞同刻，建议先完成解锁并重查捕获资格。Disabled 和 Occupied 永远不会被重复解锁效果重新开放。

洞状态转换、黑球移出模拟和 UI 进度由真实提交层一次完成；预测、入洞动画、重复碰撞回调都不能再次计数。最后黑球入洞后的场景收尾由 Session 统一执行，不能由 PocketBase 直接结束游戏。

## 9. 架构与目录归属

关于图形实例组织层，新增[图形交互管理职责评估](数学桌球-图形交互管理职责评估.md)：建议补充 GeometryManager 与 GeometryView，负责图形集合、关联与表现，几何判定和反弹仍复用本方案的规则与共用模拟。此项是待确认架构建议，尚未创建脚本。

管理器由既有 GameManager 持有，沿用普通 C# 生命周期；不增加全局单例或额外 TEngine 框架模块。


PocketBase 管理同一种洞的不同状态即可，初版无需为 Locked、Unlocked、Occupied、Disabled 各写一个 MonoBehaviour 子类。若没有不同洞行为，也不为六个位置创建六个类。PropBase 与 PocketBase 分属不同职责，几何触发计算通过规则对象复用，不通过强迫二者共享复杂继承树来复用。

原 BilliardsGoalJudge 的几何计算可迁移或重命名为 GeometryInteractionJudge，保留已有数学求解，不再调用 Session.Win；通关由 Session 的全黑球入洞统计判断。

进入顺序为关卡数据 → 台面布局 → 球集合、六洞、道具 → 世界状态与 Session → 输入驱动。退出先解绑驱动和预测，再清理 Session 及各管理器，最后卸载台面。Prefab 子对象跟随根对象回收；单独异步加载的球和道具由对应持有者释放。

## 10. 力度与多球预测

保留力度映射到初速度、白球出杆半径和基准路程的方案，预测采用同一个全桌模拟计算。D(p) 表示白球无球球碰撞时的基准滚动距离；发生速度传递后不能强迫每颗球都再走一遍完整 D(p)。

初版可用本杆减速参数 `a = v0² / (2 × D(p))` 作为所有活动球共同的滚动减速系数，碰撞后按各自新速度重算停球时间。质量、恢复系数与减速系数统一配置；只有一个位置写计算，预测与真实状态共用。

主预测线显示白球轨迹，保持虚线和末端实心圆点；经过库边、封闭洞口和交互圆反射后继续绘制，碰撞黑球后根据白球真实响应继续预测。建议另外显示被撞黑球的较淡虚线和预计入洞标记，否则只看白球线无法解释能否完成黑球目标；这项辅助显示属于建议。

全桌预测副本必须包含各黑球的位置／速度／半径、六洞状态及占用、交互触发记录、道具消费状态与白球趋势。它可以在副本里解锁洞或标记入洞，但不能让真实洞提前开放、隐藏真实黑球或改变 HUD 进度。

虚线按累计路径长度维持一致密度，缓冲区复用；末端圆点表示该球预测停止或离桌位置。对白球预计落洞要显示犯规提示，不能把该位置显示成黑球进洞成功。力度更大意味着初始运动预算更大，但受到球碰撞与入洞的影响，某条可见路径未必单调变长。

图形触发后不会截断预测，球洞解锁会影响后续黑球路径；一个洞预测接收第一颗黑球后应关闭，第二颗的路线按封口反弹重新计算。输入、球布局、洞状态或交互版本变化时更新预测，未变化时使用缓存。

## 11. 配置与表现

配置表分类与字段归属按[多关卡配置表分类方案](数学桌球-多关卡配置表分类与字段归属方案.md)展开：建议 5 张关卡主表／明细表与 4 张共用参数表，所有关卡共用同一套表，通过 LevelId 区分；该分类待确认后才修改实际源表。本节下表是业务数据类别概览，不表示每一行都需要单独建表。

LevelManager 继续从现有 Luban Tables 读取配置，并提供只读业务数据；运行状态独立保存在世界状态中。

| 配置内容 | 必要字段／约束 |
|---|---|
| 关卡 | 白球与黑球定义引用、MaxShots、六洞配置、几何规则与道具引用 |
| 球定义 | 唯一 BallId、类型、出生位置、半径、质量及尺寸变化能力 |
| 六洞 | 固定 PocketId、初始状态、洞口／捕获参数、关联解锁规则；不自由添加第七个洞 |
| 几何交互 | RuleId、唯一条件、图形数据、允许作用球类型、触发周期、EffectType 与关联对象 ID |
| 道具 | PropId、类型、位置、触发方式、尺寸及每杆使用限制 |
| 运动 | 力度范围、Dmin／Dmax、恢复系数、滚动减速与接触容差 |

库边缺口、六洞口、黑球、几何交互和道具都是世界空间对象，HUD 显示“已进黑球 / 总黑球”、剩余机会、当前白球大小趋势、道具状态。洞使用锁、开放、已占用、禁用的明确图标区别，不只依赖颜色。

设置、开始、暂停和返回沿用现有入口。资源继续通过 GameModule.Resource 异步加载，释放方式与持有方式配对；窗口通知使用 GameEvent、监听使用 AddUIEvent；业务留在 GameLogic 热更程序集。配置生成类和 bytes 不手改，实施时按 luban-dev 更新源表并使用项目生成流程。

配置源目前在仓库根目录 Configs/GameConfig；后续实现确需同步那里关联的表定义与数据。本轮只写 UnityProject/Docx 文档，没有修改仓库级配置。

## 12. GitHub 参考与实现选择

已检索并查看公开仓库说明，未复制、安装或运行它们：

- [Unity 官方 PhysicsExamples2D](https://github.com/Unity-Technologies/PhysicsExamples2D)：作为二维碰撞特性与接触行为的官方参考；是否采用原生物理仍要结合项目变半径和连续几何规则判断。
- [AR-Billiard](https://github.com/wby1905/AR-Billiard)：README 描述使用 Unity 物理模拟球，杆球碰撞另行计算。可参考球与击球输入的职责区分，不适合将 AR／MRTK 场景整体引入当前二维项目。
- [unity-billiards-trajectory](https://github.com/vonWolfehaus/unity-billiards-trajectory)：参考实际模拟与预测共用行为的思路；项目既有数学模拟仍应保持单一运动来源。
- [billiard-unity](https://github.com/Symbolzzz/billiard-unity)：README 仍将球物理、瞄准与游戏规则列为进行中或计划内容，不把它当成已经完成且验证过的全套方案。

建议继续扩展现有连续轨迹计算，而非同时让 Rigidbody2D 和自定义模拟推进同一球。新增黑球使事件数量、同刻接触和局部前向查询更复杂，实施前要按本方案明确世界状态与碰撞响应，不只新增 BlackBall 贴图。

## 13. 实施顺序与检查边界

确认后按依赖顺序实施：

1. 明确剩余建议规则，迁移关卡数据为白球、黑球集合、固定六洞与几何交互数据。
2. 扩展 BallBase 与 BallManager，增加 BlackBall；建立 PropManager／PropBase／FlipProp 和 PocketManager／PocketBase／PocketState。
3. 抽取多球世界状态及共用模拟，加入球球速度传递、库边与洞口连续接触。
4. 接入四状态球洞的捕获提交、单球单洞占用与全黑球通关统计。
5. 将几何目标改为道具触发或洞解锁，保留每图形唯一条件及条件圆反弹规则。
6. 接入力度映射、多球预测、虚线和圆点，更新 HUD、暂停、下一杆、重开与退出生命周期。

遵循单一职责和合成复用：输入只属于白球；球管理、洞状态、道具、几何计算、世界运动和本局结算分别负责自己的数据。只为真实扩展点使用基类或接口，避免为四个枚举状态强行建立类层次。

用户明确要求检查后，才进行编译、测试和 Unity 运行验证。拟检查重点为：四种洞状态、六洞位置、黑球唯一计数、同洞双球竞争、解锁与入洞同刻、球球链式碰撞、白球增长挤压、预测副本隔离、全部黑球通关与重开复位。

需要额外关注的成本是多球事件求解、前向几何放行查询和预测刷新开销；洞容量满足不等于关卡可解。白球犯规、口部尺寸、解锁依赖和各球摆位需要在后续获授权的试玩中确认，本轮不声称已验证可解性或性能。
