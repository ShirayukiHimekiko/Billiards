# 数学桌球：道具组件化与模拟解耦设计方案

日期：2026-10-11  
状态：待确认，仅设计；未修改道具代码或 Prefab，未运行编译、测试或 Unity 验证。

## 1. 目标与当前事实

目标是在道具 Prefab 上放一个统一的道具 MonoBehaviour，由它通过接口查找同物体上的功能 MonoBehaviour。添加或替换道具功能时，应能从 Prefab 的组件组成看出实际行为，同时保持真实物理世界与轨迹预测一致。

当前代码和资源呈现出三个分离且重复的行为来源：

1. `PropManager` 加载 Prefab，获取 `PropBase`，但通过 `PropEffects.Get(data.Kind)` 从配置枚举另行取得纯 C# 效果。`PhysicsWorld` 在未传入效果时还会再次按枚举创建。
2. 除钥匙外的八个道具 Prefab 均挂 `FlipProp`；`FlipProp` 本身为空，Prefab 上的脚本名称不代表其实际效果。钥匙挂 `KeyProp`，只处理隐藏表现。
3. `IPropEffect.Apply(SimulatedBall, float)` 仅适合改球的效果。钥匙、加杆、显露和预演仍由 `PhysicsWorld` 按 `PropEffectKind` 分支处理；部分效果类的 `Apply` 为空。扩展道具时容易同时修改配置转换、工厂、物理世界和 Prefab。

这些是当前代码与 Prefab 的事实，不代表所有枚举都必须删除。`PropEffectKind` 目前还服务配置校验和 UI 快照，迁移时要分别处理其用途。

## 2. 推荐结构

```text
关卡配置：摆放、次数、作用域、参数、Prefab 地址
                         │
                         ▼
Prefab：PropObject（统一根 MonoBehaviour）
        ├─ FlipPropAbility / KeyUnlockPropAbility / ...（功能 MonoBehaviour）
        └─ 可选表现组件（可用状态、音效、动画等）
                         │ 初始化时通过接口查询并生成只读效果规格
                         ▼
PropManager：加载、绑定、校验、按配置顺序收集规格、同步表现、回收
                         │
                         ▼
PhysicsWorld：只接收效果规格和关卡配置；持有使用次数与持续状态
        └─ Copy / Predict 共享只读规格，复制可变世界状态
```

### 2.1 根对象与功能组件

- `PropObject : MonoBehaviour` 承担位置/尺寸初始化、通用视觉状态和同一 GameObject 上的能力查询。不要在根组件中写 `switch(kind)`，也不要为每种道具保留一个空的 `PropBase` 子类。
- 功能组件实现小接口，例如 `IPropSimulationProvider`。`FlipPropAbility : MonoBehaviour, IPropSimulationProvider` 明确挂在翻转 Prefab 上；钥匙 Prefab 挂 `KeyUnlockPropAbility`。根对象初始化时查询一次并缓存。当前每个道具要求恰好一个主要玩法功能组件；可选的表现功能使用独立接口。若以后允许多个玩法效果，再定义显式执行顺序和叠加规则，不能依赖 `GetComponent` 返回的首个组件。
- 接口查询可以封装为 `GetRequiredFeature<T>()` / `GetFeatures<T>()`。缺失、重复或与配置不符时在关卡初始化阶段报带道具 ID 和 Prefab 地址的错误。初始化时查找一次即可，物理步进和预测循环中不调用 `GetComponent`。
- `PropManager` 只认识根对象和接口，不认识 `FlipPropAbility` 等具体类。功能组件只负责声明/构建自身能力，管理器仍负责一组道具的加载与释放。

### 2.2 预测与真实世界的边界

**不建议把场景 MonoBehaviour 直接作为 `PhysicsWorld` 长期持有的效果对象。** 当前 `PhysicsWorld.Copy()` 会共享 `_propEffects`，而 `Predict()` 和几何门试算都会创建世界副本。若效果 MonoBehaviour 后来保存次数、触发标记、动画状态或访问 GameObject，预测可能改变真实表现，且 Prefab 销毁后副本会留下无效引用。

推荐让功能 MonoBehaviour 在初始化时提供一个不依赖 Unity 场景对象的**只读效果规格**（可以继续使用现有 `IPropEffect` 的纯 C# 实现作为过渡）。参数由 `PropPlacementData` 注入；次数、持续杆数、洞状态等可变值继续保存在每个 `PhysicsWorld` 中。真实世界与预测共享只读规格，复制各自的可变状态。场景视觉反馈只在真实世界同步时调用功能/表现组件。

接口形状示意，命名和参数在实施时按现有代码细化：

```csharp
public interface IPropSimulationProvider
{
    IPropSimulationEffect CreateEffect(PropPlacementData data);
}

public interface IPropSimulationEffect
{
    PropEffectResult OnTrigger(PropEffectContext context);
}
```

`PropEffectContext` 只暴露效果需要的模拟数据；`PropEffectResult` 表达加杆、解锁目标洞、开启显露/预演等结果，由世界统一写入状态。翻转、反转、冻结等效果修改传入的模拟球。此示意描述职责，不是可直接粘贴的最终 API；应先列出九种效果及持续规则，再决定结果字段和是否需要 `OnShotStart` 等窄接口。尤其不能把钥匙继续塞进一个空的 `Apply(ball)`。

### 2.3 配置的职责

- Luban/关卡配置仍决定摆放位置、资源地址、触发半径、使用次数、作用域、持续杆数和倍率。Prefab 的功能组件决定**执行什么效果**，避免“Prefab 看起来是翻转道具，运行时却由枚举变成冻结道具”的双重来源。
- 迁移期间保留 `PropEffectKind` 作为配置与 UI 的兼容字段，在初始化时核对配置种类和功能组件种类。全部 Prefab 完成迁移后，再评估 UI 是否仍需该枚举；若需要，可由功能规格提供只读类型标识，不应再次按枚举选择执行类。
- `PhysicsWorld` 的无参数效果回退路径 `PropEffects.Get(level.Props[i].Kind)` 目前仍存在。待所有调用方能显式提供规格后，移除这条隐式工厂路径；需要无场景模拟的调用方应显式构建规格，避免运行时与无场景运行采用两套行为来源。

## 3. 模式与原则的取舍

| 原则/模式 | 在本项目中的落点 |
| --- | --- |
单一职责 | 根对象管通用对象行为，能力组件管功能声明，Manager 管集合生命周期，World 管模拟状态。 |
开闭原则 / 策略模式 | 新增普通效果时增加能力组件和纯模拟效果，挂到 Prefab；不再扩充 `PropEffects` 的选择分支。特殊效果也应逐步转为效果结果，减少 `PhysicsWorld` 的类型分支。 |
里氏替换 | 不依赖 `FlipProp : PropBase` 这类空子类表达类型；根对象保持一致的初始化和可用状态契约。 |
接口隔离 | 改球、世界结果、持续效果、表现回调按真实需要拆分；钥匙功能不实现无意义的改球方法。 |
依赖倒置 | `PropManager`、`PhysicsWorld` 依赖能力/效果接口，不依赖每种道具的具体组件。 |
迪米特法则 | 外部只向 `PropObject` 请求能力或规格，不穿透 Prefab 子节点查具体组件。 |
合成复用 | 通过 Prefab 组合根对象、玩法功能和表现功能，替代大量空子类。 |

不要为满足原则而引入通用注册中心、反射扫描、复杂技能树或新的 asmdef。现有 `GameLogic` 目录的 `Module/Core` 是职责组织：`PropManager` 和管理契约仍在 `Module/PropModule`；道具根对象、功能 MonoBehaviour、纯模拟效果在 `Core/Prop`；`PhysicsWorld` 仍在 `Core/Physics`。现有 UI 和 `UIModule` 不属于本次方案范围。

## 4. 实施顺序与风险

1. **建立单一能力入口（中风险）**：引入统一根组件与功能接口，在九个 Prefab 中明确挂对应功能 MonoBehaviour；逐一核对 `.meta/GUID` 和现有资源引用。Unity 资产修改通过项目规定的 Unity CLI/AssetDatabase 路径进行，避免文本直接改写 Prefab 引用。
2. **接入模拟规格（中风险）**：`PropManager` 从根对象取得只读规格并按关卡配置顺序交给 `PhysicsWorld`；明确规格数量、顺序和有效期。保留真实与预测共用一套规格、分别持有可变世界状态。
3. **收敛特殊分支（较高风险）**：逐一迁移钥匙解锁、加杆、显露、预演和持续效果规则，形成效果结果/窄接口；这些分支影响预测、UI 与结算，不应在第一步一次性重写。
4. **移除旧入口（中风险）**：所有 Prefab 与无场景调用方完成迁移后，删除空的类型子类、旧工厂和重复的枚举选择。配置枚举如果仍服务 UI/内容标识，保留其数据职责。

实施时需要检查的行为边界：九类道具的触发与消耗；单杆/整关作用域；持续杆数；钥匙解锁与拾取反馈；加杆；显露/预演；重新开始；真实轨迹与预测轨迹的一致性。此处只是后续检查清单，尚未执行验证。

## 5. 外部方案评估

- [Unity Open Project #1 架构概览](https://github.com/UnityTechnologies/open-project-1/wiki/Game-architecture-overview)：其角色对象以运行时组件组合能力，数据与场景组件分工明确。可借鉴组合方式；其 ScriptableObject 状态机和事件通道超出本项目道具需求，不建议整套引入。
- [Unity FPS Sample 源码说明](https://github.com/Unity-Technologies/FPSSample/blob/master/Documentation/SourceCode.md)：将能力控制、对象表现和效果分开，可借鉴职责边界；其 ECS、网络同步和系统规模不适合直接移植到当前桌球项目。
- [Unity Data-Driven Ability System](https://github.com/DanAndDev/unity-data-driven-ability-system)：展示了效果管线以及只读定义与运行时状态分离，但仓库是小型示例，适合作为模式参考，不宜作为成熟依赖引入。
- [Unity `GetComponent` / `GetComponents` 文档](https://docs.unity3d.com/ja/6000.0/ScriptReference/GameObject.GetComponents.html)：多个能力组件应显式收集和管理；`GetComponent` 返回首个匹配组件，不应承担多个功能的顺序约定。

结论：建议采用 **统一道具 MonoBehaviour + Prefab 上的接口功能 MonoBehaviour + 纯数据模拟效果规格**。它保留你希望的 Unity 组件化编辑体验，同时适配本项目会复制模拟世界做预测的事实。
