# 数学桌球：图形交互管理职责评估

日期：2026-10-06 · 任务等级：L4 · 状态：架构建议，待确认后纳入实现。

关联：[黑球入洞与六洞状态主方案](数学桌球-黑球入洞与六洞状态架构方案.md)。本轮只归档架构判断，不创建业务脚本，不修改配置或资源，不运行验证。沿用本会话已经查询的 tengine-dev 架构、模块、热更、事件、资源与命名规范。

## 1. 判断与原因

**按当前一关多个图形、每图形一种条件、各自关联道具或球洞的需求，建议新增 GeometryManager 和 GeometryView。** 图形集合的注册、关联、状态表现与复位已经形成独立职责，继续全部放进 BoardView 或 Session 会使这两个对象承担过多的图形细节。

但“有反弹”本身不要求新增管理器。反弹是共用模拟中的接触响应；解锁判定是纯几何查询；管理器承担图形实例生命周期与映射。不能把这三者合成一个既管理对象、又自行 Update 推球、又直接操作洞状态的脚本。

此前主方案已经规划 GeometryInteractionJudge 和 BilliardsContactQuery，但没有明确谁组织多个图形实例及其状态显示。本建议补齐这个组织层，不再增加第二套几何求解或反弹算法。

## 2. 建议的最小职责划分

图形数据的配表细节见[多关卡配置表分类方案](数学桌球-多关卡配置表分类与字段归属方案.md)：图形、唯一条件和关联效果同属 TbLevelGeometry 的一行，GeometryManager 接收 LevelManager 构建的只读数据，不各自读表，不因增加管理器就新增一张对应的参数表。

| 类型 | 职责 | 不承担的职责 |
|---|---|---|
| GeometryManager（新增普通 C# 类） | 注册图形、维护 RuleId 到配置与视图的映射、提供只读规则集合、同步显示、按触发周期复位、解绑释放 | 不读 Luban 表、不计算速度、不另存一份洞状态、不每帧自行扫描并提交触发 |
| GeometryView（新增 MonoBehaviour） | 绑定 RuleId，显示图形轮廓、唯一条件圆、未触发／已触发表现和必要反馈 | 不解锁真实洞、不触发真实道具、不判通关、不修改球体 |
| GeometryInteractionJudge（主方案已有规划） | 根据球状态与图形数据判断条件，求连续区间最早达成时刻，返回带 RuleId 的结果 | 不持有场景对象，不调用动画、PocketManager 或 UI |
| BilliardsContactQuery + BilliardsSimulation（主方案已有规划） | 计算交互圆接触、条件放行、反弹及剩余轨迹；真实与预测共用 | 不在另一脚本内重复推进同一个球 |

GeometryInteractionData 继续作为只读配置，包含图形、条件、关联效果和对象 ID。图形的已触发／本杆已消费等运行状态统一属于 BilliardsWorldState，GeometryManager 根据这份状态刷新视图，不再独立维护可以与世界状态分叉的 Triggered 字段。

推荐目录：

```text
Module/GeometryModule/GeometryManager.cs
Core/Geometry/GeometryView.cs
Core/Geometry/GeometryInteractionData.cs
Core/Rules/GeometryInteractionJudge.cs
```

前两项是本轮新增建议，后两项是主方案已有的数据与规则职责落位。数据不因目录调整再定义一套重复类型。所有类型仍放现有 GameLogic 热更程序集。

## 3. 调用与状态提交

```text
LevelManager：读取并校验图形配置与关联 ID
→ GameManager：创建／持有 GeometryManager，组织初始化
→ GeometryManager：绑定多个图形视图，提供只读规则
→ 共用模拟：查询当前全桌最早事件，判断几何条件或反弹
→ 效果提交：更新对应洞／道具及几何触发状态
→ GeometryManager、PocketManager、PropManager：同步各自表现
→ Session：发布界面快照并判断全部黑球是否入洞
```

效果计算在共享世界状态中完成，Session 的真实提交层协调管理器同步。几何对象不直接持有某个球洞 MonoBehaviour 引用，通过 RuleId、EffectType 和 TargetId 关联，避免与洞生命周期耦合。

解锁、图形消费标记与阻挡变化在同一模拟事件中提交，然后重查剩余时间；UI 的 GameEvent 通知在提交后发布，不用异步通知或显示动画决定本次球洞是否可接球。一个洞仍保持 Locked、Unlocked、Occupied、Disabled 的状态权限，重复几何事件不能把 Occupied 或 Disabled 重新开放。

例如图形 G1 的唯一条件关联 PocketId=TopLeft。白球达成条件时，共用计算产生 UnlockPocket 结果；真实提交使左上洞从 Locked 变为 Unlocked，并将 G1 的本局触发标记置为完成。若达不到条件，则由模拟在相应交互圆接触处反弹，G1 的几何条件和洞状态均保持原状态。

解锁用图形按本局周期复位；关联翻转道具的图形可按每杆消费周期复位。两个周期由已有交互数据明确指定，不能 GeometryManager 每次下一杆都清空所有图形。

## 4. 真实模拟与预测的边界

预测复制 BilliardsWorldState 中的图形、洞、道具和球状态，再调用同一个 Judge、接触查询和模拟计算。预测中可以达成 G1 并开放副本中的左上洞，但不调用真实 GeometryManager 的状态提交、PocketManager 的解锁或视图动画。

这样可以同时保证“预计解锁后的黑球路线会变化”与“松开鼠标前真实洞仍然上锁”。GeometryView 的隐藏或提示显示开关只影响显示，不决定阻挡是否参与计算。

各视图不添加独立 Update 计算碰撞或逐帧检查解锁。同步由事件结果驱动，预测变更由输入和世界状态版本驱动，避免随着图形数量增加产生重复扫描和每帧分配。

## 5. 当前不建议增加的类

当前没有明确的图形子类行为，先用一个 GeometryView 配合图形数据绘制。不为了同时存在几个三角形就增加 GeometryBase、TriangleGeometry、InnerGeometry、OuterGeometry 等层次；内切／外切属于条件数据，不各建一个管理器。

未来如果不同图形有不同的场景组件、动画或独立行为，再评估 GeometryBase／具体子类。数学公式是否支持任意多边形仍是单独的问题，新增基类不能自动解决它。

GeometryManager 由 GameManager 持有，沿用 BallManager、PropManager、PocketManager 的普通管理器模式；无需新的全局单例、框架模块接口或程序集。采用这个划分会增加一个生命周期参与者，因此进入、重开、退出和异步取消的绑定与清理都要成对落实。

## 6. 参考与建议边界

本轮重新查看 [Unity 官方 PhysicsExamples2D](https://github.com/Unity-Technologies/PhysicsExamples2D) 与 [unity-billiards-trajectory](https://github.com/vonWolfehaus/unity-billiards-trajectory) 的项目说明：前者提供二维物理示例，后者利用隐藏物理场景生成球轨迹。它们作为碰撞与预测复用的背景参考，没有提供本项目“图形关联解锁六洞”的直接管理器方案。

因此，是否增加 GeometryManager 的判断来自本项目已有职责与当前需求，不是宣称外部库要求如此。建议新增实例组织层，同时复用主方案已经规划的规则和模拟层。
