## 1. 当前事实与问题

- `Core/Ball/WhiteBall.cs`、`BlackBall.cs` 当前均为空子类。
- `BallBase` 持有序列化的球面、阴影、碰撞体、击球组件及尺寸趋势组件引用；初始化时要求所有球都有 `BallSimulationComponent`，按配置球种判断是否需要击球组件。
- `BallBase.ApplyState` 按黑球/白球与增长趋势选择颜色，导致基类直接了解各球种的专属行为。
- `BallSimulationComponent` 只镜像 `Growing`，没有运动求解或半径演算；真正的半径变化、运动、碰撞和落袋判定位于纯数据的 `BilliardsWorld`。
- `BallManager.Sync` 当前对全部球调用 `Simulation.SetGrowing`，因此黑球也被迫持有无实际用途的趋势组件。
- 两个球 Prefab 使用 `Surface` 和 `BallShadow` 子节点，球面是 `SpriteRenderer`，阴影是 `MeshRenderer`。根节点上的 `GetComponent<SpriteRenderer>()` 无法取得球面；按明确路径获取可以直接表达组件所属的固定节点。
- `Tools/BilliardsTableAuthoring.cs`、`Tools/BilliardsMultiBallAuthoring.cs` 依赖旧序列化字段绑定或复制，职责调整时需要同步修改。

## 2. 职责分配

| 归属 | 应负责 | 不应负责 |
| --- | --- | --- |
| `BallBase` | 共用组件获取与缓存；保存表现状态；位置、半径、球面缩放、阴影、滚动 Shader 同步；出生状态恢复；共用初始化与释放顺序 | 白球输入、蓄力、增长趋势；按球种选择颜色；碰撞求解；通关与犯规判定 |
| `WhiteBall` | 获取、初始化、重置及释放击球组件和尺寸趋势组件；公开白球的 `Shoot` 能力；根据世界快照同步趋势并决定白球颜色 | 每帧自行推进世界运动；直接结算白球落袋或通关 |
| `BlackBall` | 决定黑球颜色；承接将来确有需求的黑球专属表现 | 持有击球或尺寸趋势组件；统计剩余黑球或占用球洞 |
| `BallShootComponent` | 瞄准、蓄力、取消蓄力、提交击球意图 | 决定真实轨迹、碰撞或落袋 |
| `BallSimulationComponent` | 本次保留现有类型，仅供白球镜像尺寸趋势 | 作为所有球必需的组件；独立演算运动或半径 |
| `BilliardsWorld` | 共用时间轴、运动、球球碰撞、库边碰撞、半径变化、道具与落袋计算；提供可复制的预测状态 | 获取 Unity 组件或引用球表现对象 |
| `BilliardsSession` 等规则层 | 白球犯规后的流程、黑球进度与通关结算、出杆次数和暂停 | 将结算逻辑分散到表现子类 |

基类同步任意球的半径，不等于基类负责改变半径。白球专属的是增长/缩小能力与趋势表现；通用的是把模拟得到的半径正确显示出来。

黑球可以继续保持很轻的子类，不为增加类内代码而创造额外职责。

## 3. 共用入口与差异扩展

采用浅继承配合已有能力组件，不引入新的管理器或复杂策略框架：

1. `BallBase` 提供固定的初始化、重置、状态同步、释放入口，保持共用生命周期顺序。
2. 通过必要的受保护扩展点调用子类的组件绑定、专属状态同步、颜色选择及生命周期操作；扩展点名称和粒度在实施时保持精简。
3. `Shoot`、`Simulation` 以及对应字段从基类移至 `WhiteBall`，使黑球不再暴露不存在的输入和尺寸趋势能力。
4. `BallManager.Sync` 统一把 `SimulatedBall` 快照交给表现同步入口。基类读取通用状态，白球在扩展点读取 `Growing` 并更新其趋势组件，黑球不处理趋势。
5. 表现只读取世界快照，不修改其中的物理状态，也不持有快照来形成第二份权威世界。
6. 保留现有 `BilliardsSession` 对具体 `WhiteBall.Shoot` 的调用方式；真实模拟及预测继续使用 `BilliardsWorld`。

这样基类无须判断 `BallKind.White/Black` 来决定组件依赖和颜色。配置与 Prefab 类型匹配的边界检查仍由 `BallManager` 负责。

本次不同时拆分 Luban 表结构、重写物理世界或重命名所有组件。`BallSimulationComponent` 的名称确有歧义，但它目前只是趋势镜像；后续确有独立需求时再评估重命名或直接合并到白球表现。

## 4. 组件自动获取

默认使用代码获取本球内部组件，去除这些组件引用的 Inspector 拖拽依赖。

| 所需引用 | 获取方式 | 所属类 |
| --- | --- | --- |
| 根节点碰撞体 | `GetComponent<CircleCollider2D>()` | `BallBase` |
| 球面节点 | `transform.Find("Surface")` | `BallBase` |
| 球面渲染器 | 从已找到的 `Surface` 调用 `GetComponent<SpriteRenderer>()` | `BallBase` |
| 阴影节点 | `transform.Find("BallShadow")` | `BallBase` |
| 击球组件 | `GetComponent<BallShootComponent>()` | `WhiteBall` |
| 趋势组件 | `GetComponent<BallSimulationComponent>()` | `WhiteBall` |

- 在现有显式 `Initialize` 的组件绑定阶段获取一次并缓存，后续状态同步和输入直接使用缓存。这与当前由管理器加载后显式初始化的流程一致，也不依赖跨组件 `Awake` 调用顺序。
- 对同节点必需依赖使用 `RequireComponent`：所有球需要 `CircleCollider2D`，白球另外需要击球与趋势组件。黑球没有白球能力依赖。
- `RequireComponent` 只约束同节点组件，不能创建所需球面/阴影子节点，也不能假定它会自动补齐所有已有 Prefab，因此仍需迁移已有资源。
- 必需依赖只在初始化边界报告缺失，并提供球 ID 和节点/组件名称；正常同步路径不重复判断。销毁及异步加载边界仍依据生命周期需要处理失效引用。
- 不使用模糊的 `GetComponentInChildren<SpriteRenderer>()` 来选择球面；当前结构下明确的子节点路径足够，无须新增标记组件。
- 会话、台面等外部依赖继续由管理器/会话注入。`GetComponent` 只能取得相应 GameObject 上的组件，不能替代所有跨对象依赖。
- 自动获取组件不意味着删除全部 `SerializeField`；材质、贴图等需要资源配置的内容仍遵循各自的资产配置职责。

## 6. GitHub 参考与采用判断

- [Unity Open Project 的 SoundEmitter](https://github.com/UnityTechnologies/open-project-1/blob/main/UOP1_Project/Assets/Scripts/Audio/SoundEmitters/SoundEmitter.cs) 使用 `RequireComponent` 声明依赖，并在 `Awake` 中通过 `GetComponent` 缓存引用。借鉴依赖声明和一次获取的做法，本项目缓存时机采用已有显式初始化流程。该仓库已停止开发，仅作为已有实现参考，不引入其整体架构。
- [Unity GetComponent API](https://docs.unity3d.com/ScriptReference/Component.GetComponent.html) 明确其查询范围为同一 GameObject。
- [Unity RequireComponent API](https://docs.unity3d.com/ScriptReference/RequireComponent.html) 说明依赖添加发生于添加组件时，并不自动修复全部已有组件实例的缺失依赖。

这一需求通过现有 Unity API 和项目的能力组件即可实现，不需要新增组件缓存插件或物理库。
