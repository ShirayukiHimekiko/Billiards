## 1. 游戏由哪些部分组成

| 部分 | 负责什么 |
|---|---|
| 游戏入口 | GameManager 管理开始游戏、界面切换与整体生命周期 |
| 关卡管理 | LevelManager 读取、校验并提供关卡数据，组织桌面与目标的准备、卸载 |
| 本局流程 | BilliardsSession 统一管理操作许可、滚动与成功结果；之后再补失败、杆数和重开 |
| 球对象管理 | BallManager 管理当前白球、初始化、复位和释放 |
| 球的基础行为 | BallBase 实现初始化、显示、位置与大小同步、复位，WhiteBall 表达白球类型 |
| 操作控制 | 击球组件统一处理瞄准、蓄力、出杆和取消 |
| 白球模拟 | 模拟组件统一计算运动、减速和大小变化；道具阶段再接趋势翻转 |
| 三角形目标 | 显示 LevelManager 提供的三角形，目标显示与判定共用数据 |
| 成功判定 | BilliardsGoalJudge 独立计算内切、外接与最早达成时刻，由本局流程调用 |
| 翻转道具 | 接触后改变球的大小变化方向 |
| 界面提示 | 显示力量、剩余杆数、球的状态和目标提示 |
| 结果处理 | 显示成功或失败，提供重试和重开 |

## 2. 各部分怎样配合

玩家操作决定方向和力量，白球按规则滚动。滚动期间，判定部分持续检查目标、道具和边界。游戏流程根据检查结果决定继续滚动、通关或失败，界面同步显示当前情况。

完整流程中，Session 统一管理剩余杆数和最终结果；LevelManager 管配置，BallManager 管球对象，球模拟负责状态演进，判定器只返回目标结果，界面负责显示。避免多个部分同时决定成功、失败或扣杆，也不把运行状态写回关卡配置。

当前先完成关卡数据管理与静态判定；运动区间查询与停球反馈随后接入。具体职责与模式依据见[架构评审](../数学桌球-架构评审与目标判定职责设计.md)，关卡数据归属见[关卡管理器设计](../数学桌球-关卡管理器设计.md)。

关卡与玩法参数统一采用[Luban 配置表](../数学桌球-Luban配置表与数据分层设计.md)：关卡表保存布局和目标参数，球参数表合并击球、运动与大小变化参数。配置基础设施异步准备后，由 LevelManager 转换为只读业务数据，分别交给显示、本局和 BallManager；生成记录不直接作为可变运行状态。生成代码属于 GameProto，管理器和具体业务仍按 Module/Core 分类。

## 3. 需要准备的内容

- 一张桌面、一颗白球、一个三角形目标、一个翻转道具。
- 一套瞄准箭头、力量条、杆数和状态提示。
- 成功、失败、重开和暂停提示。
- 可调整的关卡设置：摆放位置、出球大小、运动速度、变大变小的速度和贴合宽松程度。

## 4. 制作原则

使用现有 Unity 项目和项目框架。先实现规则，再添加画面反馈。关卡设置集中调整，常用球体和提示尽量复用。暂停、退出和重开都要恢复到明确的状态。

脚本摆放按[实际目录约定](../数学桌球-脚本目录归属约定.md)：管理器在 Module/xxModule 分类，具体业务在 Core/Ball、Level、Rules、Session、Item、Events 分类，球组件集中在 Ball/Components；窗口沿用 UI 及实际生成器配置。目录分类与功能拆分分别处理，同类功能继续合并。

本版只制作一个完整关卡。后续新增关卡或黑8玩法时，再扩展相应部分。
