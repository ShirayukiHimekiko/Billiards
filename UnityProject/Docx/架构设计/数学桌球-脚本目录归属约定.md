## 1. 已确认的分类规则

按用户最新要求，管理器放在已有 `GameLogic/Module/` 下，以 `xxModule` 命名分类目录；小球等具体业务内容放在已有 `GameLogic/Core/` 下，再按职责分类。窗口继续放在 `GameLogic/UI/`，生成绑定代码按实际 UI 生成器配置输出。

本次的 `xxModule` 指目录分组，管理器类名继续使用已确定的 GameManager、LevelManager、BallManager。根目录现有 `GameModule.cs` 是统一模块访问入口，与拟建 `Module/GameModule/` 文件夹分别承担不同职责。目录归属不改变 GameManager 的单例、LevelManager/BallManager 的持有关系或 TEngine 模块注册方式。

## 3. 初版目录归属（历史，当前以新规范为准）

业务根目录为 `Assets/GameScripts/HotFix/GameLogic/`。以下保留目录设计，初版已按职责落位；具体已创建文件见初版实施记录，预留内容不视为已实现。

```text
GameLogic/
├── GameApp.cs
├── GameModule.cs                 现有统一模块访问入口
├── Module/
│   ├── GameModule/
│   │   └── GameManager.cs
│   ├── LevelModule/
│   │   └── LevelManager.cs
│   ├── BallModule/
│   │   └── BallManager.cs
│   └── UIModule/                 已有 UI 管理实现
├── Core/
│   ├── Ball/
│   │   ├── BallBase.cs
│   │   ├── WhiteBall.cs
│   │   └── Components/
│   │       ├── BallComponentBase.cs
│   │       ├── BallShootComponent.cs
│   │       └── BallSimulationComponent.cs
│   ├── Level/
│   │   └── BilliardsLevelData.cs
│   ├── Rules/
│   │   └── BilliardsGoalJudge.cs
│   ├── Session/
│   │   ├── BilliardsSession.cs
│   │   └── BilliardsUISnapshot.cs
│   ├── Item/                     道具数据与显示脚本，类型沿用实际实现
│   └── Events/                   业务命令和通知接口
├── UI/
│   ├── StartUI.cs
│   ├── MainUI.cs
│   ├── SettingsUI.cs
│   └── Gen/                      按实际生成器配置生成
└── SingletonSystem/              已有通用单例基础设施
```

树中省略既有 asmdef、.meta 和无关框架文件。关卡桌面与目标显示脚本归到 Core/Level，球状态与出杆数据归到 Core/Ball，目标判定结果归到 Core/Rules，本局状态归到 Core/Session；具体类型名以实际实现为准。

| 脚本或内容 | 当前归属方向 | 实施时处理 |
|---|---|---|
| GameManager | `GameLogic/Module/GameModule/` | 保留游戏入口、开始函数、管理器持有与生命周期职责 |
| LevelManager | `GameLogic/Module/LevelModule/` | 管理关卡读取、校验、准备与卸载 |
| BallManager | `GameLogic/Module/BallModule/` | 管理球的创建、查找、复位与清理 |
| BallBase、WhiteBall、球状态与出杆数据 | `GameLogic/Core/Ball/` | 球的基类、具体类型与自身数据 |
| BallComponentBase、BallShootComponent、BallSimulationComponent | `GameLogic/Core/Ball/Components/` | 组合式球能力；击球与模拟保持两类完整功能 |
| BilliardsLevelData、桌面与目标显示脚本 | `GameLogic/Core/Level/` | 关卡数据和具体场景内容；管理器在 Module/LevelModule |
| BilliardsGoalJudge、判定结果与必要几何方法 | `GameLogic/Core/Rules/` | 独立纯规则计算，供本局调用 |
| BilliardsSession、BilliardsUISnapshot、本局状态 | `GameLogic/Core/Session/` | 当前局流程、结果与用于 UI 刷新的快照 |
| 道具数据与具体显示脚本 | `GameLogic/Core/Item/` | 实施第六步时沿用已有类型，不为目录新增道具管理器 |
| IBilliardsUI、IBilliardsCommand 等业务事件定义 | `GameLogic/Core/Events/` | 命令与通知接口；复用事件机制与实际事件组 |
| StartUI、MainUI、SettingsUI 等窗口实现 | `GameLogic/UI/` | 遵守实际 UI 生成器配置及 Prefab 节点绑定 |
| UI 自动生成绑定代码 | 生成器配置指定的位置 | 三个窗口绑定已由原生成器输出到 `GameLogic/UI/Gen/` |
| 既有 UIModule 实现 | `GameLogic/Module/UIModule/` | 维持其 UI 框架职责；普通玩法管理器不因类名带 Manager 就自动成为框架模块 |
| 既有 Singleton 基础设施 | `GameLogic/SingletonSystem/` | 保留通用单例实现；业务 GameManager 不放进这里 |

UI 路径依据 `Assets/Editor/UIScriptGenerator/ScriptGeneratorSetting.asset`：当前 `impCodePath` 为 `Assets/GameScripts/HotFix/GameLogic/UI`，`genCodePath` 为 `Assets/GameScripts/HotFix/GameLogic/UI/Gen`，命名空间为 `GameLogic`。这是默认设置；实施时仍需核对具体 Prefab 绑定组件是否覆盖路径。当前不预设 `UI/Billiards/`，也不更改生成器设置。

UI 窗口类名省略项目名前缀，使用 `StartUI`、`MainUI`、`SettingsUI`；前两者全屏，设置为非全屏弹窗。若后续确需独立结果、暂停或加载窗口，分别按用途命名为 `ResultUI`、`PauseUI`、`LoadingUI`。类名不决定资源地址：已有示例 `MainUI.prefab` 保留，拟建主界面资源暂定 `GameMainUI`，设置暂定 `SettingsUI`，由 Window 特性绑定，实施时核对唯一性。

普通 C# 类和 MonoBehaviour 可以位于同一业务程序集，继续使用现有 GameLogic 程序集与命名空间。分类目录不要求新增 asmdef，也不要求把所有 Manager 改为 XxxModule 类或新增 IXxxModule 接口。

Module 中的管理器负责组织、持有与生命周期，Core 中的对象实现具体行为或规则。GameManager 持有两个管理器与 Session；BallManager 管理 BallBase；Session 使用关卡数据、球状态和规则计算。球基类继续负责初始化、显示、位置大小同步、复位，规则计算继续由独立判定器完成，目录调整不重分这些职责。

## 4. 初版实施约定（历史）

- 管理器和具体业务按上述分类落位，类型名和文件名核对已有实现后沿用，避免创建第二份同职责脚本。
- 后续实际移动已有脚本时，通过 Unity Pipeline 保留 .meta/GUID 并核查 Prefab、场景和生成绑定引用；先找到用户已经完成的功能所在分支与目录，再决定迁移清单。
- 尚无脚本的分类目录随对应步骤创建；本轮文档更新不在 Assets 中创建空文件夹。
- 事件定义归到 Core/Events，继续复用已有事件组；当前未发现 IEvent 目录，不把它写成现有目录。
- UI 实现与生成绑定代码按当时生成器/Prefab 配置分别放置。

配置采用[Luban 数据分层](数学桌球-Luban配置表与数据分层设计.md)：源表在仓库根目录 Configs/GameConfig/Datas，当前文件为 Level.xlsx、Ball.xlsx；生成代码目标在 UnityProject/Assets/GameScripts/HotFix/GameProto/GameConfig，生成 bytes 目标在 UnityProject/Assets/AssetRaw/Configs/bytes。它们不随业务分类移动到 Core 或 Module。LevelManager 经 ConfigSystem.Instance.Tables 查询与转换，归 Module/LevelModule；关卡快照归 Core/Level，球参数业务数据归 Core/Ball；无需另建同职责管理器。规则整改时已按确认的补充方案注册两表、隔离导出并导回必要产物；ConfigSystem、ExternalTypeUtil 和模板保持原样，不能将本次前置恢复理解为配置加载框架重构。Prefab、美术资源仍沿用实际收集和绑定。
