# 第 8 点：六洞数量决策执行方案

## 1. 目标

明确 v0.3 是否继续固定六洞，再决定保留当前硬约束还是改为关卡配置驱动；在策划确认前不擅自删除或扩展数量限制。

## 2. 当前实现与差异

- 当前 `LevelData`/`LevelManager` 对洞数量存在六洞硬约束。
- 当前黑球数量也按 1～6 做了范围限制。
- v0.3 明确定义洞的四态和钥匙绑定，但没有明确继续固定六洞。

## 3. 执行步骤

1. 由策划确认六洞是 DEMO 固定规则，还是仅为历史候选方案。
2. 若固定六洞：保留数量校验，统一配置文案、错误信息、运行时状态命名和四态映射。
3. 若改为可配置数量：移除数量硬编码，使用洞 ID、数量、绑定钥匙和黑 8 统计配置驱动，并检查 UI 布局容量。
4. 统一洞态命名为 `Disabled`、`Locked`、`Unlocked`、`Occupied`，清理 `Opened` 等旧语义混用。
5. 将数量决策同步到钥匙表、洞表、黑球通关统计、Prefab 槽位和关卡校验文档。
6. 在关卡准备阶段对洞 ID、黑 8 数量、钥匙引用和状态组合做显式校验。

## 4. 影响范围

`LevelData`、`LevelManager`、`PocketManager`、洞配置、黑球统计、钥匙绑定、UI 布局和关卡校验。

## 5. 依赖与待确认

这是第 7 点钥匙方案的前置决策，也是 HUD 洞态布局的前置决策。未确认时不得把六洞限制改成可配置，也不得把六洞继续描述为 v0.3 已定规则。

## 6. 交付边界

本方案只处理数量和状态语义决策，不新增洞类型，也不改变黑 8 的通关条件。
