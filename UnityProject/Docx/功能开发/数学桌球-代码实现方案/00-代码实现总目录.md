## 1. 按什么顺序制作

| 步骤 | 任务 | 主要制作内容 | 做完后怎样检查 |
|---|---|---|---|
| 01 | [可运行的单关卡基础](01-第一步-可运行的单关卡基础.md) | 接入启动入口；读取关卡数据；显示桌面、白球、目标、道具；统一坐标和尺寸 | 从项目正常入口进入，能看到正确关卡；修改关卡数据后显示跟着改变 |
| 02 | [瞄准与蓄力](02-第二步-瞄准与蓄力.md) | 鼠标方向、瞄准箭头、按住蓄力、方向锁定、松开出杆、取消 | 可以提交一次有效出杆；取消不会出杆或扣杆；滚动时屏蔽再次出杆 |
| 03 | [固定路程运动](03-第三步-固定路程运动.md) | 直线滚动、逐渐减速、到达计划路程后停止 | 没有提前结束时，不同力量走相同路程；大力用时更短 |
| 04 | [球的大小变化](04-第四步-球的大小变化.md) | 大力出球更大；滚动中持续变大或变小；大小上下限 | 变化连续，切换不跳变，球不会变成无效大小 |
| 05 | [内切与外接判定](05-第五步-内切与外接判定.md) | 检查完整时间区间；途中达成即停球；停止时补查 | 两种目标都能成功，短暂贴合不会漏掉 |
| 06 | [翻转道具与连续事件](06-第六步-翻转道具与连续事件.md) | 圆周接触、每杆一次、趋势翻转、时间顺序与同刻冲突 | 高速接触不漏判，触发后重算本步剩余时间 |
| 07 | [三杆尝试循环](07-第七步-三杆尝试循环.md) | 扣杆、失败复位、成功和失败结果、重开 | 扣杆准确，第三杆可成功，重开完整恢复 |
| 08 | [完整界面与生命周期](08-第八步-界面与生命周期.md) | 提示、窗口、暂停失焦、退出与加载失败重试 | 显示与实际状态一致，退出后无旧对象或反馈 |
| 09 | [关卡调试与最终验收](09-第九步-关卡调试与最终验收.md) | 通关用例、难度调整、回归与性能检查 | 正常操作有解，关键用例通过，留下实际验收记录 |

全部九步已分别展开为独立文档，使用“目标—文件职责—制作顺序—流程—验收”的结构。按顺序阅读与开发，每一步使用上一阶段的成果，补齐当前能力。文档不列完整变量表，也不提前生成游戏代码。

## 2. 代码按什么结构组织

业务代码属于现有热更程序集 `Assets/GameScripts/HotFix/GameLogic/`。文件摆放统一按[当前目录归属约定](../../架构设计/数学桌球-脚本目录归属约定.md)：三个管理器分别放 Module/GameModule、Module/LevelModule、Module/BallModule；具体业务在 Core/Ball、Level、Rules、Session、Item、Events 分类，球组件集中在 Core/Ball/Components。窗口沿用实际 UI 与生成器配置。下表按职责列出对应目录；核心对象仍使用 GameManager、LevelManager、BallManager、BallBase、两个球能力组件、Session 与 GoalJudge。

| 部分 | 负责什么 | 首次制作步骤 |
|---|---|---|
| Module/GameModule | GameManager 组织菜单进入、异步准备、应用退出和清理 | 开始界面与 01 |
| Module/LevelModule、Core/Level | LevelManager 管理读取、校验与生命周期；关卡数据和桌面目标显示在 Core/Level | 01 基础；05 补独立管理器 |
| Module/BallModule、Core/Ball | BallManager 管理球，BallBase 与 WhiteBall 实现球基础行为 | 01 |
| Core/Level、Core/Ball、Core/Item | 桌面与目标、白球、道具显示按所属内容归类 | 01；道具行为在 06 |
| Core/Ball/Components | BallShootComponent 合并瞄准、蓄力、出杆与取消 | 02 |
| Core/Ball/Components | BallSimulationComponent 合并移动、减速、半径变化及查询段 | 03—04 |
| Core/Rules | 独立 GoalJudge 及必要接触/边界数学方法，只返回规则结果 | 05—06 |
| Core/Session | 本杆状态、三杆机会、复位、结果与重开 | 02 起逐步补充，07 完成 |
| Core/Events | 界面与业务之间的命令、通知接口 | 需要时逐项补充 |
| UI | 游戏信息、交互按钮和结果窗口 | 02 起添加必要反馈，08 完成 |

UI 窗口实现沿用实际 `GameLogic/UI/`，绑定代码按生成器及 Prefab 配置输出，主界面统一为已规划的 MainUI。业务事件定义归到 Core/Events，复用已有事件组；当前未发现 IEvent 目录，不把它写成现有位置。具体业务按 Core 的分类落位，管理器按 Module/xxModule 落位。关卡与玩法参数统一采用[Luban 配置表](../../架构设计/数学桌球-Luban配置表与数据分层设计.md)，取代早期 JSON 建议；生成代码在 GameProto，LevelManager 转换为 Core 中的只读数据，后续参数按步骤增量补入表。

用法：输入把操作交给本局管理；本局管理驱动运动和判定；显示层根据结果更新对象；界面通过项目事件机制接收状态。球的坐标、半径和杆数在业务数据中保存，图片和文字只负责展示。

单关卡先使用普通 C# 类和必要的显示组件，不增加 ECS、额外程序集或独立框架。跨模块事件使用 `GameEvent`，窗口监听使用 `AddUIEvent`；本局内部由同一管理对象协调。

## 3. 全程遵守的实现约定

- 资源放到现有 `Assets/AssetRaw/` 收集目录，通过 `GameModule.Resource` 异步加载。加载的关卡根对象销毁时归还资源，手动加载的数据资源配对释放。
- 使用原有 `GameApp.Entrance` 热更入口，保留事件初始化与启动链。桌球业务写入 `GameLogic`，不放到主包流程或框架代码里。
- 桌面、球心、道具、三角形顶点使用统一的二维关卡坐标。界面坐标不参与玩法判定。
- 后续运动使用固定模拟步长；输入与画面显示可以按渲染帧更新。一次模拟步内进一步检查事件发生时刻，处理高速漏判。
- 同刻冲突按“出界 → 成功 → 道具 → 停止”处理。一次有效出杆只提交一次、只扣一次杆、只结算一次。
- 每一步完成局部验收再继续；最终通关、稳定 60 帧和重复游玩结果需要实际运行确认。

暂停与加载状态的补充规则：蓄力时暂停或失焦先取消本杆准备；失焦后需要确认继续；恢复不补算暂停时间。加载失败单独显示原因与重试，不能当成三杆耗尽。退出沿用退出应用行为；Editor 中结束 Play Mode，Player 中退出进程。StartUI、MainUI 全屏；设置按[四类音量方案](../数学桌球-设置界面与四类音量设计.md)独立分步接入非全屏 SettingsUI。存档、制作详情继续保留占位。
