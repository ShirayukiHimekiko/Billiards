# 第 5-A2 步：静态内切与外接判定

日期：2026-10-06 · 版本：v0.1 · 任务等级：L3 · 状态：实施设计已展开，功能待制作

前置：[5-A1：最小关卡数据管理](05-A1-最小关卡数据管理.md)。整体安排见[第五步：加入目标判定](05-第五步-内切与外接判定.md)，职责依据见[架构评审](../../架构设计/数学桌球-架构评审与目标判定职责设计.md)。本次只继续文档，功能接入仍需先完成 5-A1 验收。

## 1. 本步目标

给定一个时刻的白球球心与半径，判断它是否满足三角形的内切或外接条件。先用固定数据验证规则正确，再进入运动区间查询。

这一阶段的“达成”只表示几何关系满足规则。桌面边界、事件先后、是否已经结算由后续本局流程决定；此处返回的几何结果不能直接当成游戏通关。已有击球、运动和大小变化继续沿用。

## 2. 判定器与数据流

使用普通 C# 规则对象 `BilliardsGoalJudge`，内切和外接组织为内部方法，统一返回结果。它不继承 `BallComponentBase`，不挂在白球上，不增加目标管理器或单例，也不为两种规则分别建立策略类。

数据流为：LevelManager 提供只读目标与容差 → 调用方取得同一时刻的逻辑球状态 → GoalJudge 计算 → 调用方读取结果。本步固定数据验收可以直接调用判定器，不需要提前实现完整 Session。

判定器不持有 LevelManager、BallManager 或 UI 引用，不通过全局入口找球，也不在 Update 中读取图片、Transform 或碰撞回调。它不能移动球、修正半径、改变关卡配置或发送成功事件。

脚本归属遵循[目录约定](../../架构设计/数学桌球-脚本目录归属约定.md)：BilliardsGoalJudge、判定结果与必要几何方法放 Core/Rules，关卡数据放 Core/Level，球状态放 Core/Ball；LevelManager 在 Module/LevelModule。实施时复用已有类型与实现，目录分类不增加判定管理器或策略类。

## 3. 输入与输出约定

| 输入 | 约束 |
|---|---|
| 球心 `C`、半径 `r` | 来自同一逻辑时刻；坐标与半径有限，`r > 0` |
| 三角形顶点 `V1、V2、V3` | 使用 5-A1 校验后的只读数据；顶点互不重合、不共线 |
| 三条朝内单位法线 | 与顶点顺序对应，由目标准备阶段预计算；输入顺时针或逆时针应得到同一规则结果 |
| 贴合容差 `T = FitTolerance` | 有限且 `T ≥ 0`，与半径、距离采用相同长度单位 |

所有输入统一使用既有桌面本地坐标和长度单位，不能混用屏幕像素、世界坐标与本地坐标。球的图片缩放不直接参与计算。

输出至少表达“输入是否有效”和“目标类型”。目标类型为未达成、内切、外接；输入非法与合法但未达成必须能区分。非法数据返回明确原因，由调用方处理，不当作一次正常击球失败，不自动改写输入。

本步不返回命中时间；静态查询只有一个给定时刻。可提供三条边或三个顶点的距离误差供验收检查，但不为调试信息建立新管理器。同一份输入重复查询应得到相同结果，查询不保留本局成功状态。

## 4. 内切判定

每条边取起点 `Vi` 和朝内单位法线 `ni`，计算球心到该边所在直线的有符号距离：

`di = dot(ni, C - Vi)`

朝内为正、朝外为负。先检查球心在三角形内部或边界，即三条 `di ≥ 0`；再检查三条边都满足：

`|di - r| ≤ T`

两项同时成立才返回内切。单位法线必须归一化，不能用未归一化的法线把距离随边长放大。

球心的内外检查只允许处理浮点误差的微小数值余量，不能使用玩法容差 `T` 放宽到三角形外。圆周贴合则允许配置容差内的微小越边，因为 `di - r ≥ -T` 已由贴合条件约束。

不能先把 `di` 取绝对值再判断：三角形外的旁切圆也可能与三条边所在直线等距。只接近内心、圆完全位于三角形内、或仅贴住一两条边，都不能替代三边贴合条件。

## 5. 外接判定

计算三个顶点到球心的距离：`qi = length(Vi - C)`。三个顶点都满足以下条件才返回外接：

`|qi - r| ≤ T`

三个顶点需要贴近圆周。仅把三角形包在圆内、或只有一两个顶点贴近圆周，都不算外接。外接球心可能位于三角形外，不能沿用内切的球心内部检查。

如实施时使用平方距离，应比较 `max(0, r - T)² ≤ qi² ≤ (r + T)²`，保持与原规则等价。不能把 `|qi² - r²|` 直接与长度容差 `T` 比较，两者单位不同。

## 6. 容差、边界与结果选择

贴合区间包含边界，误差恰好等于 `T` 也算达成。数值余量仅处理运算误差，必须与玩法容差分开，并与输入的长度尺度相适应；不能为了通过示例扩大玩法容差。

`T = 0` 是有效输入；浮点计算仍按明确的数值精度处理。三角形退化判断属于数据有效性检查，不能借用贴合容差判断是否共线。窗口大小、贴图尺寸和帧率不改变几何规则。

两种规则任意一种成立即可返回对应类型。若因容差较宽同时成立，固定返回内切，与整体第五步约定一致。优先级只解决结果选择，不改变任一种判定的数学条件。

桌面出界检查不放入静态判定器。后续 Session 需要确认整个球处于有效桌面内，并比较出界与目标时刻，才能决定实际成功；相同时刻仍按整体规则优先处理出界。

## 7. 固定数据验收

以下均为验收用数据，不是实际关卡配置。使用非等边直角三角形：`V1=(0,0)`、`V2=(6,0)`、`V3=(0,8)`，边长为 6、8、10。内切圆为 `C=(2,2), r=2`，外接圆为 `C=(3,4), r=5`；默认示例容差 `T=0.05`。

| 场景 | 球状态 | 预期结果 |
|---|---|---|
| 标准内切 | `C=(2,2), r=2` | 内切 |
| 标准外接 | `C=(3,4), r=5` | 外接 |
| 内切误差在容差内 | `C=(2,2), r=2.04` | 内切 |
| 内切误差超出容差 | `C=(2,2), r=2.06` | 未达成 |
| 外接误差在容差内 | `C=(3,4), r=5.04` | 外接 |
| 外接误差超出容差 | `C=(3,4), r=5.06` | 未达成 |
| 圆位于内部但未贴边 | `C=(2,2), r=0.5` | 未达成 |
| 只贴两条边 | `C=(4,1), r=1` | 未达成；三条距离为 1、4、1 |
| 旁切圆误判检查 | `C=(12,12), r=12` | 未达成；朝内距离含 `-12`，球心在外部 |
| 大圆包住三角形 | `C=(3,4), r=7` | 未达成；三个顶点距离为 5，均未贴近圆周 |
| 只有一个顶点在圆周 | `C=(0,0), r=6` | 未达成；三个顶点距离为 0、6、8 |
| 两种条件同时成立 | `C=(2,2), r=2, T=6` | 内切；仅用于验证结果优先级，不采用为关卡默认容差 |

还需逐项检查：

- 三个顶点的六种排列结果一致；三角形和球一起平移、旋转后结果一致；等比例缩放时半径和容差也同步缩放，结果一致。
- 用容差边界及边界两侧的状态验证包含关系，区分玩法误差和数值误差。
- 钝角三角形的外心在三角形外，正确外接圆仍达成外接。例如 `(0,0)、(4,0)、(1,1)` 的外接圆为 `C=(2,-1), r=√5`。
- 非有限坐标或半径、非正半径、负数或非有限容差、重复顶点及共线顶点返回输入无效；不得产生 NaN 传播或正常未达成结果。
- 重复查询不改变球状态、目标快照或其他查询结果；不触发停球、提示或游戏状态变化。

## 8. 制作顺序与通过标准

先明确输入有效性和统一结果，再完成内切及旁切圆反例，最后完成外接及大圆反例。每一项验收通过后再制作下一项，不在这一阶段提前接入运动区间或通关反馈。

本步通过标准：两种正例、反例、容差边界、顶点顺序和非法输入都符合约定；判定只依赖传入数据，球组件没有新增目标规则。后续实施时完成有意义的纯逻辑检查；只有需要检查现有坐标接入与显示一致性时，再按项目流程验证 Unity 运行。
