# 数学桌球：击球力度驱动成长速率方案

日期：2026-10-07 · 任务等级：L3 · 状态：已实现（代码与源表已改，待导表与运行验证）

> **半径语义已于同日第二轮修订**：白球不再是"出杆瞬间被赋成力度对应尺寸"，而是**出生 0.28、按力度决定的速率上涨、且跨杆保留**。第 3.2 / 3.3 节基于旧语义的推论已作废，一切以**第 8 节**为准。

## 0. 先说结论

需求"力度越大，成长速率越大"在当前代码里确实不存在：`PhysicsWorld.RadiusRate` 直接返回配置常量 `BallConfigData.GrowRate`（0.12），与 `Shoot` 的 `power` 无关。补上这个映射本身很小（约 5 处改动）。

但落地前有两个既存约束会让这个功能**看起来没生效或产生反效果**，必须先决策：

| 约束 | 位置 | 影响 |
|---|---|---|
| 洞口捕获半径只有 0.58 | `Board.xlsx` 的 `pocketLayouts.captureRadius` | 白球半径超过 0.58 就**永远无法落袋**，而现状下约 7% 力度就会超过 |
| 白球半径上限 1.6，满力度起始半径已是 1.0 | `Ball.xlsx` 的 `radiusMax` / `shotParams.radiusMax` | 满力度的增长空间只有 0.6，除以约 4.5 秒运动时间，速率上限约 0.13。**想要 3 倍速率差异就必须同步放宽 `radiusMax`** |

所以本方案分两部分：Part A 是纯代码映射（必做），Part B 是数值与洞口决策（需要你拍板）。

## 1. 现状确认

### 1.1 力度已经在哪些地方生效

`PhysicsWorld.Shoot`（`Assets/GameScripts/HotFix/GameLogic/Core/Physics/PhysicsWorld.cs:360`）已经对 `power` 做了三处线性映射：

```csharp
float radius  = Mathf.Lerp(config.ShotRadiusMin, config.ShotRadiusMax, power);   // 第 364 行
float speed   = Mathf.Lerp(config.SpeedMin,      config.SpeedMax,      power);   // 第 394 行
float distance= Mathf.Lerp(config.DistanceMin,   config.DistanceMax,   power);   // 第 395 行
_deceleration = speed * speed / (2 * distance);                                  // 第 397 行
```

没有映射的是成长速率。`Shoot` 里唯一与生长相关的语句是 `white.Growing = true;`（第 399 行），只重置趋势，不涉及速率。

### 1.2 速率当前的唯一来源

`PhysicsWorld.RadiusRate`（同文件第 516 行）：

```csharp
float rate = ball.Growing ? config.GrowRate : -config.ShrinkRate;
```

`config.GrowRate` 来自 `BallConfigData`（`Module/BallModule/BallConfigData.cs:74`），直接透传 Luban 的 `SizeChangeParams.GrowRate`。当前 `Ball.xlsx` 白球行是 `{"growRate":0.12,"shrinkRate":0.12}`，即力度 0 与力度 1 完全相同的固定值。

### 1.3 下游链路已经参数化，无需改动

这点很关键，说明改造是**加法而不是重构**：

- `BallTrajectory`（`Core/Ball/BallTrajectory.cs:33`）的 `RadiusRate` 是构造参数，`At(time)` 按 `Radius + RadiusRate * time` 线性插值。
- `Prepare`（`PhysicsWorld.cs:489`、`:505`）在每个固定步开始时重新取一次 `RadiusRate(ball)`，并按 `(limit - radius) / rate` 截断到半径上下限。
- `ContactSolver.Circle`（`Core/Physics/ContactSolver.cs:35`）用 `a.RadiusRate + b.RadiusRate` 参与接触方程，本身支持速率非零。
- `GoalJudge.FindGoal`（`Core/Rules/GoalJudge.cs:98`、`:102`、`:108`）同样把 `trajectory.RadiusRate` 代入多项式。
- `Predict`（`PhysicsWorld.cs:1111`）走 `Copy()` → `Shoot()`，与真实模拟同一条路径。

结论：**只要速率在 `Shoot` 里确定并随球保存，预测线、几何门判定、碰撞都会自动跟随。**

### 1.4 唯一的真实风险点

`SimulatedBall.Copy()`（`PhysicsWorld.cs:51`）逐字段复制可变状态。目前它复制了 `State`、`Active`、`Growing`。新增的速率字段**必须加进这里**，漏加会导致预测线与实际模拟不一致——而且这种不一致在有碰撞时才会暴露，属于难查的静默 bug。

## 2. Part A：代码映射方案

### 2.1 配置层

`Configs/GameConfig/Datas/Ball.xlsx` 的 `sizeChangeParams` JSON：

```
现状：{"growRate":0.12,"shrinkRate":0.12}
改为：{"growRateMin":0.06,"growRateMax":0.18,"shrinkRate":0.12}
```

`Configs/GameConfig/Defines/game.xml` 的 `<bean name="SizeChangeParams">`（第 47~50 行）同步：`growRate` → `growRateMin` + `growRateMax`，类型均为 `float`。

> 勘误（2026-10-07 复核）：本文早前误写为 `Datas/__beans__.xlsx`。经核对，`__beans__.xlsx` 仅有表头、无任何 bean 定义；`SizeChangeParams` 实际定义在 `Defines/game.xml`，改表应改该 XML。

用 Min/Max 双端命名，与已有的 `speedMin/speedMax`、`distanceMin/distanceMax`、`shotParams.radiusMin/radiusMax` 保持同一套约定，不引入 `baseRate + multiplier` 这种新语汇。

`Module/BallModule/BallConfigData.cs` 同步替换字段并加强校验：

```csharp
public readonly float GrowRateMin;
public readonly float GrowRateMax;

// 原 GrowRate <= 0 校验替换为
GrowRateMax < 0
|| GrowRateMin > GrowRateMax
```

`GrowRateMin` 允许为 0（低力度完全不长大），所以下界是 `>= 0` 而不是 `> 0`。

### 2.2 模拟状态层

`Core/Physics/PhysicsWorld.cs` 的 `SimulatedBall` 新增一个字段：


构造函数中以 `data.Config.GrowRateMin` 初始化——未出杆时保持最低速率，行为与现状一致。

`Copy()` 补一行：

```csharp

```

### 3.2 约束一：洞口捕获半径 0.58

`FindContact` 中的落袋判定（`PhysicsWorld.cs:620`）：

```csharp
if (PocketStates[p] == PocketState.Unlocked && ball.State.Radius <= pocket.CaptureRadius)
```

`Board.xlsx` 六个洞的 `captureRadius` 全是 0.58。这不是"捕获范围"，而是**硬性准入门槛**。

对照上表最后一列：现状（固定 0.12）下，**约 7% 力度**白球终径就超过 0.58，该杆剩余时间白球不再可能被洞捕获。加入力度映射后这个阈值只会更低。

> 复核修正（2026-10-07 第二轮）：上一版此处写"白球半径每杆被重置、不跨杆累积"——**该结论已作废**，因为它依据的 `Shoot` 半径覆盖逻辑已在第 8 节移除。现行语义是白球半径**跨杆保留**，只在关卡重开 / 犯规重生时回到出生半径 0.28。因此"球长大后进不了洞"是**跨杆持续**状态，不能再靠"落袋算犯规"当作避险。
>
> 仍然成立的部分：白球落袋在 `Resolve` 的 `Pocket` 分支被判为**犯规**（`WhiteFoul = true`）。本作（数学桌球）真正的玩法约束是白球抵达目标三角形时能否恰好达到内切/外接所需半径，而非捕获半径本身。

三个处理方向：

| 方案 | 做法 | 后果 |
|---|---|---|
| B1 取消门槛 | `captureRadius` 提到覆盖 `radiusMax`（如 2.0） | 半径不再影响能否进洞，`RadiusRate` 里的守卫（贴边/重叠时返回 0）成为唯一约束 |
| B2 同步放开 | `captureRadius` 设为随 `radiusMax` 走的值，留 1.3 倍余量 | 保留"球太大进不去"的惩罚，但把门槛推到当前机制下够不到的位置 |
| B3 维持现状 | 不动 | 明确接受"白球一旦长大就废掉"是设计意图，力度只是加速这个过程 |

我倾向 **B1**。理由：现有 0.58 的门槛让 `radiusMin 0.15 / radiusMax 1.6` 这个范围里超过 73% 的半径不可用，`growRate` 这个玩法实际上一直在"快速走向废球"。若这不是刻意设计，B1 才能让力度→成长速率成为一个可玩的正反馈。

### 3.3 约束二：半径上限导致速率饱和

> 前提变更（2026-10-07 第二轮）：本节原基于"满力度出杆半径 = `shotRadiusMax` = 1.0"推导。该覆盖逻辑已移除（见第 8 节），白球从出生半径 0.28 起步，"只剩 0.6 空间"不再成立，`radiusMax` 已**回退为 1.6**。下方两张表中"出杆半径"一列随之作废；"无碰撞增长量 = 速率 × 运动时间"的算法与 `growRateMin = 0.06 / growRateMax = 0.18` 的取值仍然有效。另需注意：白球跨杆累加，实际顶到上限远早于单杆估算。

（以下为历史推导，前提已作废）满力度起始半径曾是 `shotRadiusMax = 1.0`，`radiusMax = 1.6`，只剩 0.6 空间；满力度运动时间 4.5 s。

```
不触顶的速率上限 = 0.6 / 4.5 ≈ 0.133
```

也就是说**保持 `radiusMax = 1.6` 时，速率最多只能在 0 ~ 0.133 之间拉开差异**，做不到明显的倍差。`Prepare` 会把轨迹截断在 `radiusMax`，之后 `RadiusRate` 返回 0，高力度会提前停止生长——玩家看到的是"高力度涨到头就不动了"，反而会觉得力度没用。

按 `growRateMin = 0.06`、`growRateMax = 0.18`（3 倍）重算：

| power | 速率 | 无碰撞增长量 | 出杆半径 | 基准终径 |
|---|---|---|---|---|
| 0.00 | 0.060 | 0.120 | 0.250 | 0.370 |
| 0.25 | 0.090 | 0.270 | 0.438 | 0.708 |
| 0.50 | 0.120 | 0.440 | 0.625 | 1.065 |
| 0.75 | 0.150 | 0.621 | 0.813 | 1.434 |
| 1.00 | 0.180 | 0.810 | 1.000 | 1.810 |

满力度需要 `radiusMax >= 1.81`。建议配比：

| 字段 | 现值 | 建议 | 理由 |
|---|---|---|---|
| `growRateMin` | — | 0.06 | 低力度几乎不长大，保留"轻推只是调整位置"的手感 |
| `growRateMax` | — | 0.18 | 3 倍差异，肉眼可辨 |
| `shrinkRate` | 0.12 | 0.12 不变 | 见 3.4 |
| `radiusMax` | 1.6 | 2.0 | 留约 10% 余量，避免满力度临界截断 |
| `captureRadius` | 0.58 | 见 3.2 决策 | 与 `radiusMax` 配套 |

上表是**无碰撞**基准。实际有碰撞会改变轨迹，且 `RadiusRate` 在贴边或与其他活动球重叠时返回 0（第 527~557 行），实测增长量会低于此表。`radiusMax` 留余量正是为了吸收这部分偏差。

### 3.4 待决策：shrinkRate 是否也按力度缩放

`FlipPropEffect` 翻转趋势后走 `-config.ShrinkRate`，与力度无关。这会造成不对称：大力度把球撑大后，只能靠固定 0.12 慢慢缩回来。

| 选项 | 说明 | 评价 |
|---|---|---|
| C1 只改 grow（推荐） | 严格按本次需求 | 改动面最小。代价是高力度变大的球更难缩回，但 `radiusMin 0.15` 的下限足够，不至于失控 |
| C2 grow/shrink 同步 Min/Max | 结构对称 | 需要给 `SizeChangeParams` 再加两个字段，改动翻倍。若"大力翻转道具 = 迅速缩小"是有意策略，才值得做 |

倾向 C1。翻转道具 `useLimit` 只有 1，滥用 C2 会让它同时是最强成长和最强收缩的杠杆。

### 3.5 待决策：`growRateMin` 是否允许为 0

`BallConfigData` 当前要求 `GrowRate > 0`。若希望"低力度完全不长大"，需要放宽为 `>= 0`。注意 `Prepare` 中 `Math.Abs(rate) > .000001f` 才做截断，`rate = 0` 是安全分支，不会产生除零。建议允许 0。

需求澄清：白球**不是**"出杆瞬间被赋成力度对应尺寸"，而是**出生 0.28、按力度决定的速率一路上涨、且跨杆保留**。原 `Shoot` 里的半径覆盖必须移除。

### 8.3 由此引入的两个后果（需决策）

1. **只增不减**：`Shoot` 每杆都会 `white.Growing = true`，所以白球尺寸单调上涨，只有 `FlipProp` 能反向。一关内出杆数次后必然顶到 `radiusMax = 1.6`，此后"力度越大成长越快"在该关内失去意义。

   - (ii) `CanPlace` 对白球只校验台面边界，不校验球间重叠；
   - (iii) 保持现状，接受死锁。

   倾向 (i)：复用现成通道，不影响正常解法。

## 9. 预测线忽略图形阻挡（2026-10-07 第三轮，已实现）

需求：图形（条件圆 / 三角形）对**瞄准线**相当于摆设，不是检测物体；线条穿过图形，不产生折射。

### 9.1 现状（为什么现在会折射）

图形在物理层有**两种**语义，必须分开看：

| 事件 | 位置 | 作用 | 本轮处理 |
|---|---|---|---|
| `EventKind.Goal` | `PhysicsWorld.cs:604` | `GoalJudge` 判定内切 / 外接，是**过关条件** | **保留不动** |
| `EventKind.Gate` | `PhysicsWorld.cs:653-663` | 把图形圆当**实体障碍**，`:888` 用 `GeometryRestitution` 反射弹开；仅 `CanCompleteApproach` 判定"本次接近能达成条件"时放行穿过 | 仅预测忽略 |

`Physics.xlsx` 的 `geometryRestitution = 1`，即**完全弹性镜面**，所以瞄准线撞到图形会原样弹回。

### 9.2 改动

| 文件 | 改动 |
|---|---|
| `Core/Physics/PhysicsWorld.cs` | 新增私有标志 `_ignoreGates`（默认 `false`） |
| `Core/Physics/PhysicsWorld.cs` `FindContact` | 几何门循环的跳过条件加 `_ignoreGates \|\|` |
| `Core/Physics/PhysicsWorld.cs` `Predict` | `Copy()` 之后设 `query._ignoreGates = true`，只作用于预测副本 |

`Copy()` 不复制 `_ignoreGates`，因此真实世界与 `CanCompleteApproach` 的内部副本仍为 `false`——**实球的几何门行为完全未改**。

### 9.3 ⚠️ 已知不一致（本轮决策的代价，需知悉）

预测线与实球现在**不同源**：

- **瞄准线**：穿过图形，只按库边 / 其他球 / 洞口演化；
- **实球**：仍会被图形弹开（除非 `CanCompleteApproach` 放行）。

所以**当瞄准方向会撞上图形时，虚线显示的路径与出杆后的真实路径不一致**。

两个后续开关（任选其一即可消除或坐实这个差异）：
- 想让线也不折不扣地"骗人"就保持现状；
- 想让两边一致，删掉 `Predict` 里的 `query._ignoreGates = true;` 即可回退；
- 或者反过来，把 `FindContact` 的 Gate 分支整体移除，让球也直接穿过——那时 `geometryRestitution`、`CanCompleteApproach`、`_admitted`、`_conditionLatched`、`_ignoredGeometry`、`_dryApproach`、`EventKind.Gate` 会一并成为死代码。

### 9.4 验收

- 瞄准目标三角形 / 条件圆，虚线应**直接穿过**，不再折返；
- 出杆后实球仍按原逻辑被弹开（当前预期）；
- 库边反射、球间碰撞、落袋判定不受影响。
