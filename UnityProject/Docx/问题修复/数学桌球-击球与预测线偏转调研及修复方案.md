## 1. 问题定义及判断边界

用户反馈预测线偏转夸张，垂直情况下也出现偏折，希望参考 GitHub 的成熟台球项目。

准确术语是碰撞后的偏转或反弹。必须区分：

1. 正撞静止目标球：当前项目的等质量、完全弹性、无旋转模型下，白球的法向速度传给目标球，白球应停止，不产生侧向速度。
2. 近乎正撞目标球：白球保留很小的切向速度，其方向可接近侧向，但移动距离应很短，不能因为归一化方向而画成长尾。
3. 垂直撞平直库边：应沿原路反弹；斜撞才改变方向。仅屏幕方向竖直，并不能证明垂直于实际接触法线。
4. 图形目标圆：现有预测明确忽略几何门，而真实模拟仍可能阻挡。这是已有实现的规则差异，需要与显示偏转问题分开处理。

本轮取得的是源码和配置源表证据，未复现用户画面，尚不能认定所有偏折都来自同一原因。已询问用户“垂直”具体指正撞球、撞库还是经过图形。

### 1.1 2026-10-07 截图补充结论

用户后续截图显示：大白球的预测线在接近黑球前形成折点，折点与黑球表面相隔约一个白球半径，碰撞后预测线继续沿新方向延伸。该形态不是整杆最终停点短缺，而是中途球碰撞仍用白球圆心位置作为显示折点。

物理接触条件本来就是两球圆心距离等于两球半径之和，因此白球越大，圆心折点离黑球表面越远，视觉问题越明显。现有 `ExtendPredictionToSurface` 只修改整条折线最后一个点，无法修正中途碰撞；若直接把圆心折点推到黑球表面，再与碰撞后的圆心采样点连续相连，还会制造一段不存在的斜线。

据此，本问题已具备足够静态证据，不再按单文件显示偏移处理。正确边界是：预测层输出真实碰撞事件数据，表现层把碰撞前入射段画到球面接触点，并把碰撞后的白球轨迹作为独立线段继续绘制。

## 2. GitHub 参考及成熟度评估

### 2.1 ekiefl/pooltool：物理模型的主要参考

项目面向科学与工程的台球模拟，其 README 提供 JOSS 论文及 pyOpenSci 评审信息。它适合作为碰撞模型参考；Python 代码不能直接作为本项目的 Unity 依赖。

实际读取的公开源码：

- [项目 README](https://github.com/ekiefl/pooltool/blob/main/README.md)
- [无摩擦、等质量、弹性球碰撞](https://github.com/ekiefl/pooltool/blob/main/pooltool/physics/resolve/ball_ball/frictionless_elastic/__init__.py)
- [球杆击球及旋转模型](https://github.com/ekiefl/pooltool/blob/main/pooltool/physics/resolve/stick_ball/instantaneous_point/__init__.py)
- [球碰撞的接触位置修正](https://github.com/ekiefl/pooltool/blob/main/pooltool/physics/resolve/ball_ball/core.py)
- [事件模拟与历史记录](https://github.com/ekiefl/pooltool/blob/main/pooltool/evolution/event_based/simulate.py)
- [瞄准球心与切球角计算](https://github.com/ekiefl/pooltool/blob/main/pooltool/ai/aim/core.py)
- [库边模型注册](https://github.com/ekiefl/pooltool/blob/main/pooltool/physics/resolve/ball_cushion/__init__.py)

观察：

- 无摩擦模型沿球心连线建立法向，分解相对速度：白球保留切向分量，目标球得到法向分量。没有人为添加固定偏折角。
- 击球输入包含杆速、方向、抬杆角、触球偏心等，输出线速度及角速度；侧旋相关偏转有明确模型和输入。
- 默认可复制系统进行模拟；按下一事件的精确时间推进、响应并记录历史，之后再生成连续显示轨迹。
- 接触位置修正与速度响应是不同职责；数值分离修正不应被解释为球的真实飞行轨迹。

适用结论：参考法向/切向分解、精确碰撞事件记录、模拟状态副本。保留本项目的变半径、道具及数学目标规则；本轮不引入侧旋、高低杆、真实库边摩擦等完整模拟内容。

实际读取：

- [项目说明](https://github.com/vonWolfehaus/unity-billiards-trajectory)

适用结论：借鉴“预测与实际共用输入和求解规则”。该仓库是 Unity 2019.3 示例，作者也说明维护有限，不能称为成熟商业台球成品；它按固定步采样，同样不能作为精确碰撞拐点采样的依据。本项目已有纯数据连续事件模型，替换为 Rigidbody 会引入第二套规则及额外迁移成本，不推荐。

## 3. 当前项目证据

### 3.1 击球与物理响应

- BallShootComponent 持续更新鼠标投影方向，蓄力后把同一方向、力度传给 Session.Shoot；BoardView 的预测也接收这一方向、力度。
- PhysicsWorld.Shoot 将方向归一化，根据力度映射初速、无碰撞路程、白球成长速率，使用初速平方除以两倍路程确定减速度。
- PhysicsWorld.Resolve 的球碰撞分支用两球球心连线及质量计算法向冲量，不是把目标球当成固定镜面。
- Reflect 对库边仅改变法向速度；理想垂直撞库不会凭空产生横向分量。
- ContactSolver.Circle 使用两球半径之和以及半径变化率计算连续接触时刻，不能退回零半径 Raycast 或固定直径的 ghost ball。

当前源表只读数据：Physics.xlsx 中 ballRestitution=1、railRestitution=1、geometryRestitution=1、contactTolerance=0.0001、stopSpeed=0.015、simulationStep=1/120；Ball.xlsx 中白球与黑球质量均为 1。上述仅说明配置源表，不代表已核对运行时加载的 bytes 或实例。

### 3.2 确定存在的预测显示问题

1. PhysicsWorld.Step 内部已经推进到精确接触时刻，但 Predict 仅在整个 Step 结束后添加白球位置。一个时间步内的碰撞位置没有单独输出，绘制时会跨过真实拐点连接两端，造成折点位置及局部角度失真。
2. BoardView.ExtendPredictionToSurface 无条件寻找最后一个非零位置差，并把最终点沿归一化方向延长整个 endRadius。自然停止并不意味着末端接触另一物体，因此这种外推没有普遍成立的物理依据。
3. 接触分离修正、停止前很小的位置差也可能成为上述末段方向。微小差值归一化后会得到完整单位向量，随后被扩展成一个球半径的线尾。
4. BoardView 当前把终点圆点放在已经外推后的点上，圆点不再表示预测球心的真正停点。
5. Predict 循环条件是整个世界 Moving；白球已经停止、其他球继续运动时仍重复添加白球点。这些点没有新的白球行程，应从轨迹显示中剔除。

这些是静态实现事实；它们是否完全解释用户当前画面仍需用户允许后的运行检查。

### 3.3 近正撞为什么会出现侧向短尾

对等质量、静止目标球、完全弹性、无摩擦的简化模型，令 n 为球心连线的单位法向：

- 目标球速度：v_target = dot(v_in, n) * n。
- 白球速度：v_white = v_in - dot(v_in, n) * n。

精确正撞时切向分量为零。近正撞时切向分量很小，但方向仍可与来球方向接近垂直。

若碰撞前速度与法向夹角为 θ，则白球残余速率为 |v_in| * sin(θ)；在当前恒定减速度模型下，其自然停止路程与 sin²(θ) 成正比。显示应保留这个短距离，不能把方向归一化后再额外补一个半径。此处是模型推导，不是本轮运行测量。

另一个变量是白球在运动中变大，会改变首次接触时的球心连线及切球角。标准固定尺寸台球的瞄准算法只能参考，不能直接复制其固定半径假设。

## 4. 推荐方案：先修正预测轨迹的表达

### 第一步：准确输出轨迹分段

在共用 Step/Advance 流程中提供预测专用的可选轨迹收集入口，正式推进保持原有调用方式。

- 输出球心的真实运动段端点，保留接触时刻的位置及碰撞后的下一段，不能只取固定步两端。
- 接触穿透修正属于数值约束，单独处理，不能把该偏移解释成一段运动。
- 白球停止或落袋后结束白球轨迹收集；如果后续玩法事件仍需要世界推进，允许预测副本继续推进其他球，但不继续添加白球重复点。
- 共线段合并和零长点去重仅用于显示；不能根据主观观感删掉真实碰撞或对物理方向进行角度插值。
- 保留现有预算不足的失败语义，不能把截断点标成自然停止点。

### 第二步：修正起点和终点语义

- 初始入射线从当前白球表面开始，裁剪只针对初始运动段，不能因距离过短而沿碰撞后的折线继续消耗整个半径。
- 移除自然停点的无条件半径外推；自然停止标记放在真实球心停点。
- 若需要表示预计接触球面，使用实际碰撞事件的球心、半径、接触法线求接触点，作为独立接触提示，不能把它冒充整杆终点。
- 极短残余路径按显示分辨率或位移阈值省略线段，物理结果保持不变；不得凭空增长线段长度。阈值在实施时根据现有台面尺度确定，不在本轮擅自改配置。

### 第三步：按截图修正球碰撞处的显示语义

- 预测结果为白球与其他球的碰撞记录接触时刻、两球圆心、白球半径及接触法线；接触点由事件状态计算，不由 `BoardView` 根据采样折线猜测。
- 碰撞前的白球入射段终点落在黑球表面的实际接触点，解决大球时肉眼可见的半径级空隙。
- 碰撞后的白球圆心轨迹另起一段，不能从球面接触点直接连回碰撞后的圆心采样点。虚线相位可跨段延续，但网格几何必须断开。
- `GeometryGraphic` 增加多段路径输入能力，仍复用现有网格缓存和 dash/gap 算法，不引入新的 LineRenderer、第三方包或每帧对象分配。
- 本轮只修复白球预测线与黑球接触位置，不额外新增黑球运动方向线或 ghost ball；后两项仍属于可选功能。

首轮预计修改范围：Core/Physics/PhysicsWorld.cs、Core/Level/BoardView.cs、Core/Level/GeometryGraphic.cs，并新增一个仅承载预测路径分段与球碰撞接触语义的小型数据类型。不引入第三方依赖或额外物理引擎。

### 可选后续：增加目标球方向提示

当前只绘制白球轨迹，正撞时白球停止，玩家不易看到黑球将沿哪个方向运动。可以在首次球碰撞处显示独立的目标球短指引，长度根据目标球速度或明确的辅助线样式确定，白球线与目标球线区分显示。

这属于额外显示功能，建议在首轮修复之外单独确认；不为了让线条显得自然而修改球碰撞冲量公式。

## 5. 规则差异、成本与设计原则

- 预测设置 _ignoreGates=true，实际运动仍处理 Gate。当前文档也记载此差异，本轮不擅自撤销。它意味着这条线在几何门附近是带有规则例外的辅助线，不能承诺与实际整杆路径完全一致。若用户要求完整真实轨迹，应另外决定几何门规则。
- 不通过降低恢复系数或人为压小偏转角处理显示错误；当前球碰撞公式与 pooltool 的简化模型方向一致。
- 不增加瞄准自动吸附。近正撞与精确正撞的区别需要保留，吸附是独立的交互设计选择。
- 单一职责：求解器决定运动与接触；BoardView 决定线条和标记；显示层不反向修改物理结果。
- 合成复用：继续使用 PhysicsWorld 副本和既有连续事件，不复制另一套预测物理。
- 接口隔离：轨迹收集只向预测暴露所需数据，实际模拟不承担渲染工作。
- 开闭及里氏替换：保留现有道具、事件和世界推进语义，不为形式上的设计模式增加空接口或继承层。
- 事件点采样可减少大量共线固定步点，但完整世界模拟仍有计算成本。本轮不承诺未经运行测量的性能收益。

## 6. 用户确认后的实施顺序

1. 定义最小预测路径结果，接入真实碰撞事件点、接触法线及运动段输出，保留物理公式。
2. 将球碰撞前入射段终点放到黑球表面，并让碰撞后的白球轨迹另起一段。
3. 修正初始段裁剪、自然停止点及外推逻辑，忽略数值修正带来的虚假线尾。
4. 扩展虚线网格为多段路径输入，保持现有样式、缓存和虚线相位语义。
5. 清理白球停止后的重复采样，保持预算、落袋及完整预测结果语义。
6. 汇报具体变更，并询问是否需要检查；未经明确要求不编译、不测试、不启动 Unity。

用户要求验证时再关注：精确正撞停止、近正撞短尾、斜撞两球分量、垂直撞库原路返回、桌角同刻事件、变半径首次接触、白球先停其他球后停、落袋及预算截断，以及几何门的既有预测例外。
