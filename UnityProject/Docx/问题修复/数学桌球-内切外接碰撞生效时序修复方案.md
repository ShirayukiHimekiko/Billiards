# 数学桌球：内切／外接碰撞生效时序修复方案

日期：2026-10-07。任务等级：L3。状态：用户已确认，代码修改已完成；未运行编译、测试、Unity 或其他验证。

## 需求与术语

未击球时，内切和外接目标圆默认不阻挡球。击球后，针对运动球本次接近目标的过程，计算能否达成该图形配置的条件；能达成则放行，不能达成则产生目标圆碰撞与反弹。

沿用项目现有定义：用户口述“外切”暂对应代码的 Circumscribed（外接圆经过三角形三个顶点），内切对应 Inscribed。若用户指另一种几何关系，需要先调整判定需求。

## 当前源码事实

- `Assets/GameScripts/HotFix/GameLogic/Core/Physics/PhysicsWorld.cs` 的 `Shoot()` 先用 `CanPlace()` 检查出杆半径，随后才赋予白球速度。
- `CanPlace()` 除检查台面与其他活动球外，还无条件拒绝与有效目标圆重叠。它也被犯规后的白球复位使用，导致未出杆时目标圆已发挥阻挡作用。
- `Step()` 仅在世界存在运动球时推进。`FindContact()` 查询目标圆接触；`Resolve(Gate)` 使用 `CanCompleteApproach()` 前向推演，能达成则标记本次放行，不能达成则反弹。
- `Predict()` 复制世界并在副本中出杆、推进，预测与真实运动共用规则，不需要操作真实 Collider2D。

上述结论来自源码阅读，不代表已通过运行复现或验证。

## GitHub 成熟方案评估

参考 [ekiefl/pooltool](https://github.com/ekiefl/pooltool)，这是面向科学与工程的桌球模拟项目，提供事件检测与响应策略。其 Python 运行体系及真实桌球规则不能直接替代本项目 C# 变半径球与内切／外接玩法。

选择保留项目已有的连续事件求解和预测副本，在其内部修正碰撞生效时序；不引入新的物理依赖或第二套 Rigidbody 运动体系。

## 建议实施范围

1. 调整 `CanPlace()`，只检查台面边界和其他活动球，不把内切／外接目标圆作为待击球时的实体障碍。同步修改方法及 `Shoot()` 的文档注释。
2. 保留运动中的目标接触查询与 `CanCompleteApproach()`：在出杆后的本次接近过程中判断未来是否存在有效条件时刻，不能只检查接触瞬间是否达成。
3. 本次接近能达成条件时继续放行；明确不能达成时在圆接触位置反弹。完成条件继续沿用现有解锁球洞或触发道具行为。
4. 停球后目标圆不参与摆放和下一杆出杆检查；新杆清空原有本次放行／条件触发标记，再依据新轨迹判断。
5. 瞄准预测仍在隔离副本中模拟未来出杆结果，允许显示预计反弹，但不启用真实世界碰撞或提交目标进度。

默认不新增碰撞组件或图形级全局开关。现有 `Step()` 已以运动状态约束模拟，继续按球与图形组合管理本次放行，避免一个球的结果改变其他球的通行条件。修改优先集中于 `PhysicsWorld.cs`，只有确认后的需求确实要求额外状态时才扩展范围。

## 必须留意的边界

- “当前还没达成”不等于“本次接近不可能达成”。若在第一次接触时仅做静态判定，通常会挡住本来可达成的路线。
- 允许在目标圆内部出杆后，原有 `Resolve(Gate)` 的反弹分离会将不满足条件的球推到目标圆外缘。实施采用初始重叠放行：出杆时已重叠的球先自然离开，完全分离后解除放行，再次接近时恢复条件碰撞。初始重叠期间仍查询目标成功，不凭空挪动球，也不将该放行视为已达成条件。
- `CanCompleteApproach()` 当前会把预测预算耗尽归为 `false`。预算耗尽只能说明未算完，不能证明目标不可达；本轮先记录该既有局限，若需要完整区分“不可达”和“计算未完成”，应另行确认扩展范围。
- 未允许的球类型沿用当前运动中的阻挡规则；本方案不改变白球／黑球目标权限配置。
